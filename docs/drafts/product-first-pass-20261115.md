# GitView: продуктовая проекция первого прохода

Рабочий черновик на основе [исходного намерения](../../.specgraph/root_intent.md),
[обсуждения продукта](../product-discovery.md), [корневой спецификации](GITVIEW-SPEC-0001.yaml)
и сохранённых предложений. Он показывает, что пользователь делает и что
должно оставаться понятным, не выбирая окончательный способ реализации.
Согласованные решения и агентские рабочие уточнения различаются ниже.

Для быстрого знакомства можно начать с разделов «Зачем», «Что объединяет обзор»,
«Как человек осматривает работу», «Что видно сегодня и при фильтрации» и
«Сводка, история и внимание». Затем можно посмотреть
[открытые продуктовые решения](product-open-decisions-20261115.md): они
показывают, какие последствия ещё требуют выбора. Для оценки **всей** первой
версии нужны и остальные разделы: создание Projects, выбранные поля PR и
Issue, обязательные форматы описаний, sharing, сохранённые данные, обновление
и поведение при ошибках. Технические листья графа
не обязательны для понимания этого обзора; [оценка прохода](product-first-pass-assessment-20261115.md)
объясняет, что проверено и что остаётся за его границами.

## Зачем

GitView — компактный личный обзор GitHub для человека, у которого много
репозиториев и работы, в том числе созданной coding agents. Он помогает
увидеть текущие PR и Issue, завершение работы и места, требующие внимания.
Из объекта можно перейти к первоисточнику на GitHub; GitView не должен
заменять весь GitHub.

## Что объединяет обзор

- **Project** GitView содержит один или несколько GitHub Repository. Один
  Repository может входить в разные Projects; по умолчанию один Project
  соответствует одному Repository. Organizations — метаданные источника,
  и внутри Project могут быть Repository разных организаций.
- У Project есть собственные имя, необязательное описание и состав. Имя или
  текущий адрес Repository не определяют его идентичность: подтверждённые
  rename и transfer сохраняют тот же Repository и его участие в Projects.
  Если прежний адрес занял другой Repository, его история и состав не
  объединяются со старым; временная недоступность сама по себе не означает
  удаление.
- PR и Issue — разные объекты источника. Их связь не доказывает мотив актора
  и не превращает пару автоматически в две независимые задачи.

Основание: [правила Project](project-summary-proposal.md),
[identity Repository](GITVIEW-SPEC-0002.yaml),
[предметная модель](../../ontology/domain-model.md).

## Как появляются Projects

Пользователь подключает GitHub и выбирает доступные репозитории. После
подтверждения для них появляются Projects по правилу «один к одному»;
пользователь может создать свой Project, объединить в нём репозитории,
переименовать его или изменить состав. При этом один Repository может
оставаться в нескольких Projects. Правило «один к одному» выбрано
владельцем; создание после явного подтверждения — рабочее уточнение агента.

Например, для Repository R создан Project P; затем пользователь переименовал
P и добавил в него S. Если позже он снова выбирает R при настройке, приложение
может предложить уже существующий P или создание другого Project. Рабочий
вариант агента сохраняет специальную связь R с P и предлагает повторно
использовать P; другой вариант — дать выбрать среди подходящих Projects или
создать новый. Поскольку R вправе входить в несколько Projects, само членство
не говорит однозначно, какой из них следует предложить. Оба варианта должны
сохранять уже созданные Projects и не создавать случайный дубликат при
неясном результате предыдущего сохранения. Конкретное взаимодействие и
постоянная default association остаются предложениями, а не отдельно выбранным
правилом владельца. См. [сравнение вариантов](project-default-association-review-20261115.md).

До подключения GitView предлагает путь к GitHub, а отмена подключения
позволяет вернуться к настройке. Само подключение ещё не доказывает, что
все Repository доступны приложению или что их работа уже загружена.
Пустой результат поиска в доступной области означает отсутствие совпадений
именно там, а не отсутствие репозиториев во всём аккаунте. Частичный или
неудачный поиск должен быть отличим от такого результата и давать путь к
повтору или проверке доступа.

После создания Project его можно узнать, пока PR и Issue ещё загружаются;
не загруженный список не называется пустым. Если локальные Projects нельзя
прочитать, приложение сообщает о проблеме восстановления вместо утверждения,
что Projects нет, и не сбрасывает их автоматически. Переходы первого запуска,
подтверждение выбора и детали восстановления — рабочие уточнения агента.
См. [0022](GITVIEW-SPEC-0022.yaml), [0019](GITVIEW-SPEC-0019.yaml).

Удаление Repository из одного Project не удаляет его на GitHub и не меняет
другие Projects. У сохранённого Project должен остаться хотя бы один
Repository. Если GitView не может определить доступные репозитории, он не
должен говорить, что их точно нет. Конкретный способ подключения и изменения
состава — предмет дальнейшей проработки. См.
[0005](GITVIEW-SPEC-0005.yaml), [0019](GITVIEW-SPEC-0019.yaml).

Рабочий вариант управления предлагает также удалять локальный Project после
явного подтверждения. Например, если Projects A и B содержат один Repository,
удаление A убирает его локальную конфигурацию, но не удаляет Repository на
GitHub и не меняет Project B. Это не равнозначно общей очистке истории;
сохранение остальных локальных данных определяется отдельно. См.
[0025](GITVIEW-SPEC-0025.yaml).

## Как человек осматривает работу

1. На общем уровне видны Projects и их краткие показатели. Из Project
   доступна работа его Repository; для многорепозиторного Project доступен
   обзор состава. Для Project с одним Repository не нужен дублирующий
   промежуточный экран. Прямое открытие общей коллекции работы нескольких
   Repository — рабочее предложение агента, а не отдельно выбранный маршрут.
2. PR и Issue представлены масштабируемой сеткой в духе Photos. На плотном
   уровне можно увидеть много объектов; pinch меняет плотность и доступную
   детализацию. Плотность сама не меняет выбранный Project или фильтры.
3. Long press даёт preview выбранного объекта до открытия; должен быть
   доступный способ выполнить те же основные действия без этого жеста.
   Открытие объекта сохраняет контекст для возвращения. Исследовательский
   sliding preview и глубокий просмотр PR — отдельные будущие возможности.
   GitHub-подобный календарь также рассматривается на будущее: его клетки
   обозначают дни, а не Projects или Repository.

Например, в сетке на восемь ячеек в ряд пользователь выбирает PR №42 из
Repository B. Маленькая ячейка не обязана вместить все поля: preview может
показать название, Repository, состояние и доступные сигналы, а полный
согласованный состав остаётся доступен при открытии объекта. Если при
обновлении карточка переместилась, preview и открытие всё равно относятся к
тому же PR, а не к новой ячейке на прежнем месте. После закрытия или возврата
сохраняются применимые Project, фильтр и масштаб; позиция восстанавливается,
когда это возможно. При потере доступа нельзя сохранять приватные детали
на экране только ради непрерывности. Состав preview и точное расположение
данных — предложение агента, подлежащее проверке. См. [0093](GITVIEW-SPEC-0093.yaml).

Следующее направление — «телескоп» для плотной сетки: один подробный bubble
показывает объект под пальцем и меняет содержимое при перемещении между
ячейками, сохраняя общий обзор и не открывая каждый объект. Возможная
активация через long press обсуждалась, но её сочетание с обычной прокруткой
и статическим preview ещё нужно проверить. Прототип показывает идею; он не
доказывает поведение нативного жеста и не делает этот режим обязательным для
первой версии. См. [0015](GITVIEW-SPEC-0015.yaml) и
[описание прототипа](dense-overview-prototype.md).

Прямой вход в общую работу многорепозиторного Project и точная организация
перехода к его составу — рабочее уточнение агента; native gesture mechanics
и конкретные элементы интерфейса ещё не выбраны. Внутри одного обзора pinch
меняет плотность; будет ли он также переводить между Projects, Repository и
объектами, пока не решено. Открытие объекта отдельным действием остаётся
доступным вариантом. См. [0120](GITVIEW-SPEC-0120.yaml).
См. [0006](GITVIEW-SPEC-0006.yaml), [0074](GITVIEW-SPEC-0074.yaml),
[0015](GITVIEW-SPEC-0015.yaml).

## Что видно сейчас и при фильтрации

Today — текущая картина работы, а не выборка за календарные сутки. Она
включает применимую незавершённую работу независимо от даты её создания.
История представлена измерениями и графиками; отдельный просмотр состояния
Project на прошлую дату не является обязательным. Новое уточнение владельца:
[SpecDraft, grid-today-current-work](../../conversation_memory/sketches/gitview/revisions/a748240310ba46aca7e16424b35f2b3c/notes.hc).

Владелец выбрал для подтверждённо влитого PR: его карточка уходит из текущей
незавершённой работы, а результат отражается в метрике при достаточных данных.
Правила для PR, закрытых без merge, и закрытых Issue, а также календарь
графиков остаются открытыми.
Фильтры остаются явными. Неполный ответ GitHub не доказывает удаление,
закрытие или отсутствие источника; факты и счётчики сохраняют свои ограничения.

Счётчик или сигнал может открыть соответствующую выборку, сохраняя Project,
условие и контекст Repository. После обновления число в выборке может
измениться; это не должно незаметно менять смысл исходного показателя.
См. [0007](GITVIEW-SPEC-0007.yaml), [0092](GITVIEW-SPEC-0092.yaml).

Например, сводка показала два PR с красным CI, но к открытию списка одна
проверка прошла. При подтверждённом новом результате в списке может остаться
один PR: исходная двойка относится к прежнему наблюдению, а список — к более
новому. Если данные списка неполны, приложение показывает ограничение вместо
объяснения разницы выдуманным изменением. Пользователь может изменить или
снять фильтр; после этого список уже не выдаётся за выборку исходного сигнала.

## Что содержит объект

В обзоре PR, если сведения доступны и разрешены, можно увидеть:

- номер и идентификатор в Repository, название, описание и ссылку;
- состояние open / closed / merged, draft и labels;
- Repository, исходную и целевую ветки, ревизию, автора, запрошенных
  reviewers и связанные Issue;
- оценку review, общее число тредов и число незакрытых отдельно; счётчики
  актуальных проверок CI по красному, жёлтому, зелёному и общий;
- добавленные и удалённые строки, число изменённых файлов и коммитов; время
  создания, обновления, закрытия или merge, а также время и источник наблюдения.

Для Issue выбран обзор:

- идентификатор и номер, название, описание, ссылку, состояние и доступную
  причину закрытия, labels и тип;
- Repository, автора, assignees и milestone;
- связанные PR с различением упоминания и связи на закрытие, родительскую и
  дочерние Issue, а также что блокирует Issue и что блокируется ею;
- число комментариев и участников, общее и закрытое число непосредственных
  sub-issues; время создания, обновления, закрытия и последнего комментария,
  а также время и источник наблюдения.

Не все сведения обязаны помещаться в маленькой карточке. Список
файлов diff, содержимое review threads и отдельные прогоны CI не входят в
согласованный минимальный состав. Доступен переход к исходному объекту и
лёгкий sharing. Рабочее предложение агента — по умолчанию передавать ссылку,
не добавляя автоматически приватный текст или скриншот; получатель при этом
не получает доступ к закрытому объекту автоматически. Дополнительное
содержимое sharing ещё не выбрано. См. [0016](GITVIEW-SPEC-0016.yaml).
Если ссылка уже передана системному sharing, приложение не может обещать
отозвать её после последующего изменения доступа; момент передачи зависит
от выбранного системного механизма и потребует отдельной проверки.

Недоступное поле или неполная выборка не означают ноль или отсутствие связи.
Время наблюдения GitView не тождественно времени события на GitHub.
Например, изменение названия Issue сегодня не означает, что сегодня появился
новый комментарий. Если комментарий найден при обновлении сегодня, но написан
вчера, это два разных времени. При неполном доступе к обсуждению последнее
увиденное время не обязательно является временем последнего комментария во
всей доступной области; приложение должно сохранять ограничение охвата.
Число участников обсуждения требует дополнительного уточнения: доступный
счётчик GitHub, предложенный как источник, относится к его population `User`, но сам по себе не
подтверждает число всех возможных участников или авторов комментариев,
включая coding agents. Отдельный подсчёт авторов комментариев — рабочее
предложение агента с собственным охватом; ни один из этих показателей не
следует подменять другим. См. [0077](GITVIEW-SPEC-0077.yaml).

Например, если человек написал один комментарий, а бот — два, это три
комментария и два подтверждённых автора комментариев при достаточном охвате.
Но отдельный счётчик GitHub для участвующих `User` нельзя автоматически
назвать числом всех участников, включая бота: у него своя population.
Даже полный список авторов комментариев не обязательно описывает всех,
кто участвовал в работе над Issue. Поэтому продукту ещё нужно выбрать,
какой именно счётчик называть «участники»; отдельный счётчик авторов не
становится обязательным только из-за этого примера.

CI, review и незакрытые треды — разные признаки. Плохой CI не означает
отклонённое review; закрытая Issue не обязательно означает выполненную работу.
«Активность» пока рассматривается как возможное обозначение действий и
изменений, а не как самостоятельная сущность с утверждённым определением.
Её объём не подменяет текущее состояние PR, review или CI; по мере развития
продукта смысл может потребовать отдельного уточнения.
[Выбор PR](pull-request-ontology-options.md), [выбор Issue](issue-ontology-options.md),
[обзор PR](GITVIEW-SPEC-0041.yaml), [обзор Issue](GITVIEW-SPEC-0039.yaml).

## Зачем структурированы описания

Для новых Issue и PR в участвующем процессе согласованы разделы: проблема,
мотивация, ожидаемый результат и ссылки; для PR дополнительно — изменения
и проверка. Это помогает быстро понять, **зачем** появилась работа и что
предлагается, особенно когда её создают агенты. Авторское описание остаётся
словами автора: оно само по себе не доказывает результат или успешный CI.
Например, если описание PR называет Issue причиной работы, а GitHub показывает
между ними ссылку, можно показать оба сведения с их источниками. Это ещё не
подтверждает, какой мотив был у конкретного человека или агента, ни то, что
изменение решило Issue. Ссылка на закрытие также не означает, что закрытие уже
произошло.

Существующие и внешние объекты с другим форматом всё равно доступны: их
исходный текст нельзя заменять выдуманными разделами. Формат обязателен в
выбранном процессе создания, но конкретный способ обеспечить это ещё
предстоит внедрить; наличие шаблона само по себе не гарантирует соблюдение.
См. [0010](GITVIEW-SPEC-0010.yaml).

## Сводка, история и внимание

Сводки Repository и Project показывают открытую работу и результаты, если
соответствующие данные доступны:

- число Repository в Project и охват данных, например 4 из 5;
- открытые PR, в том числе draft, и открытые Issue — раздельно;
- сигналы внимания: PR с красным CI, ожиданием review или запросом изменений,
  незакрытые review threads и PR с ними, Issue с открытыми блокировками;
- merged PR и закрытые Issue по причинам за выбранный период; графики этих
  показателей при достаточной истории.

Например, три PR с красным CI в двух Repository — это два разных числа. Один
PR может одновременно иметь красный CI и незакрытый thread: это не две
независимые задачи. Общий итог по нескольким Projects не должен дважды считать
общий Repository и его объекты. Недоступные данные и недостаток истории не
изображаются нулём; текущие значения отличаются от событий за период.
Если известно три открытых PR в одном Repository, а данные другого не
загружены, при допустимом доступе можно показать эти три как неполное наблюдение, но не как полный
итог проекта. Если наблюдение старое, оно также не гарантирует, что сейчас
открыты хотя бы три PR: за это время состояние могло измениться. Аналогично,
после добавления ещё не загруженного Repository прежний полный итог относится
к прежнему составу, а для нового Project остаётся неполным или неизвестным.

Выбор счётчика может открыть соответствующую выборку, например PR с красным
CI по всем Repository проекта. Число проверок или тредов при этом не обязано
совпадать с числом карточек PR. Предварительная выборка «проверки и review
пройдены» рассматривалась условно: её правило не выбрано, и она не должна
выдаваться за гарантию возможности merge. См. [0012](GITVIEW-SPEC-0012.yaml),
[0013](GITVIEW-SPEC-0013.yaml).

Состав Project может меняться. Например, если Repository B добавлен сегодня,
график за прошлую неделю по нынешним A и B показывает историю нынешнего
состава, а не доказывает, что B входил в Project тогда. Такой вариант —
рабочее предложение агента; нужна ли другая историческая перспектива,
ещё предстоит определить. См. [0064](GITVIEW-SPEC-0064.yaml).

Допустим, на прошлой неделе в Project достоверно входил только A, в котором
были влиты 10 PR; B добавлен сегодня, а за прошлую неделю в B влито ещё пять
PR. При достаточных данных график **нынешнего состава за прошлую неделю**
может показать 15, а график **состава Project на прошлой неделе** — 10.
Оба ответа относятся к разным вопросам. Если прошлый состав или результаты B
неизвестны, соответствующий ответ нельзя заменять нулём; график должен показать
ограничение. Сейчас выбран только сам интерес к графикам: какая перспектива
нужна по умолчанию и есть ли достаточно истории, остаётся открытым.

График изменения работы требует определённого показателя и подтверждённых
наблюдений за соответствующее время. Фиксированная когорта PR — предложение,
не выбранное правило Today; один текущий снимок не доказывает прошлый тренд.
См. [0055](GITVIEW-SPEC-0055.yaml), [0057](GITVIEW-SPEC-0057.yaml).

Issue могла закрыться на прошлой неделе и затем снова открыться. При наличии
подтверждённого события она может учитываться в метрике закрытий прошлой недели и
одновременно показывать текущее состояние open. Два закрытия одной Issue за
период — это два события, но одна Issue; причина конкретного закрытия и полнота
истории требуют отдельных оснований. См. [0056](GITVIEW-SPEC-0056.yaml),
[0065](GITVIEW-SPEC-0065.yaml).

«Что готово» для открытого PR и ожидание ответа требуют точного смысла.
Размер обсуждения и период без новых комментариев — отдельные рабочие
предложения агента; порог 24 часа не выбирался владельцем и не доказывает,
что кто-то обязан ответить. См. [0057](GITVIEW-SPEC-0057.yaml),
[0062](GITVIEW-SPEC-0062.yaml), [0097](GITVIEW-SPEC-0097.yaml).

Например, в одном открытом PR review одобрено, но CI красный; в другом CI
зелёный, но есть запрос изменений; третий уже влит. Сводка помогает найти
первые два по разным признакам и показывает третий среди завершённых за
период. Она не обязана сводить первые два к одному вердикту «не готово»:
их причины различаются, а красный CI сам по себе не говорит, кто и что должен
исправить. Запрос review конкретному человеку можно показать как запрос;
без такого подтверждения приложение не назначает ответственного по возрасту
треда или по одному факту открытого обсуждения. Выбор сигнала ведёт к
соответствующим объектам, где можно изучить известные факты и перейти к GitHub.

Например, у одного PR открытый review-тред содержит 20 комментариев, последний
из которых написан час назад; у другого — два комментария, последний три дня
назад. По количеству сообщений первым выделится первый PR, по времени без
новых комментариев — второй. Если у третьего PR тред открыт две недели, но
последний комментарий появился сегодня, ни один из этих показателей сам по
себе не выражает длительность открытого треда. Чтобы показать такой смысл,
потребовались бы достаточные сведения о его состояниях и переходах; одно
текущее состояние не доказывает непрерывную длительность. Это примеры
разных возможных сигналов, а не выбранный критерий или доказательство, что
кто-либо должен ответить. В GitView достаточно счётчика или сводного сигнала;
читать отдельные треды и их содержимое предполагается в GitHub. См.
[0062](GITVIEW-SPEC-0062.yaml) и [0094](GITVIEW-SPEC-0094.yaml).

## Данные и визуальный характер

Приложение хранит ранее полученные данные и может показать допустимый
последний результат при ошибке обновления, обозначив время и проблему.
Обновление доступно вручную; при открытии и в фоне оно выполняется по
возможности системы и источника. Неполные, устаревшие и недоступные данные
не представляются как точный актуальный ноль. Сетевая ошибка отличается
от подтверждённого отзыва доступа. Рабочая политика предлагает ограничивать
показ затронутых приватных данных, когда приложению известно об отзыве. Но
после сбоя или восстановления старой копии сведения об отзыве могут не
сохраниться: предложенный offline-режим не гарантирует, что он об этом узнает.
Здесь предстоит выбрать приемлемый баланс приватности и доступности последних
данных; содержимое резервной копии и восстановление также остаются открытыми
вопросами. См. [0036](GITVIEW-SPEC-0036.yaml), [0122](GITVIEW-SPEC-0122.yaml).

Например, GitView сохранил название приватного PR в понедельник. Во вторник
доступ к Repository отозвали, а в среду пользователь открывает приложение
без сети. Если приложение успело узнать и надёжно сохранить этот отказ,
рабочий вариант скрывает затронутые приватные данные и показывает проблему
доступа. Если же отказ произошёл без ведома приложения или восстановлена
копия, сделанная до него, доступные локальные сведения могут выглядеть так
же, как при обычном отключении сети.

В этом случае возможны разные политики: показать последнюю разрешённую ранее
информацию с указанием времени и непроверенного текущего доступа, либо скрыть
её до нового подтверждения. Первая полезнее без сети, но может показать данные
после неизвестного отзыва; вторая лучше ограничивает этот риск, но оставляет
человека без данных и при обычном сбое связи. Время последнего обновления
не доказывает, что право доступа сохраняется сейчас. Это продуктовый выбор,
а не утверждённое поведение; он отдельно влияет на содержимое и восстановление
резервных копий.

Запрос обновления, его фактический запуск и получение результата — разные
состояния: если обновление отложено из-за ограничений, это не успех и не
обязательно ошибка GitHub. У каждого затронутого Repository или типа данных
могут быть свои время последнего наблюдения и результат. Порог для обновления
при открытии — рабочий вариант агента, а не гарантия актуальности или
установленный лимит GitHub. См. [0048](GITVIEW-SPEC-0048.yaml).

Например, при обновлении проекта из двух Repository данные одного могут
обновиться, а запрос второго — завершиться ошибкой. Пользователь должен
суметь увидеть, к какой части относится ошибка и когда были получены её
последние доступные данные; успех первого Repository не делает второй
актуальным. Если GitHub ответил, но локальное сохранение не подтверждено,
это отдельная проблема приложения: новые данные могут быть доступны в
текущем сеансе, но их сохранность после перезапуска нельзя обещать. Состояние
и доступный путь восстановления должны быть понятны без опоры только на цвет
или исчезающее уведомление; конкретный системный компонент ещё не выбран.

Направление интерфейса — нативный Apple Look, системные цвета, SF Symbols и
Liquid Glass с минимумом декоративных компонентов. Требования тестируемости,
DI, TDD и сетевых/data mocks сохранены как ожидаемые качества разработки.
FSD-iOS задаёт направление организации приложения, а SpecificationCore
предполагается использовать для подходящих доменных решений; конкретные
границы модулей и правила применения предстоит уточнить позже.
Выбор конкретного хранилища, GraphQL-операций, типов и UIKit/SwiftUI-механик
не является продуктовым результатом сам по себе.

## Критерий первого автономного прохода

[Карта открытых продуктовых решений](product-open-decisions-20261115.md)
связывает оставшиеся вопросы с узлами графа и отделяет их от дальнейшей
проверки источника и платформы.

Первый проход можно считать содержательно готовым к обсуждению, когда
пользователь узнаёт свою идею в связанных маршрутах и видит продуктовые
последствия, различия состояний и открытые вопросы; неясные места явно
помечены, а не незаметно решены как якобы утверждённые. Число узлов и
`checked` не являются этим критерием.

Более детальная стадия может доводить выбранные ветви до достаточности для
реализации и проверки. Существующие технические спецификации и исследования
сохранены для неё; их объём, точные схемы и выбранные агентом механизмы не
должны становиться скрытым условием завершения первого продуктового прохода.

## Авторская оценка первого прохода

Проекция теперь связывает основные согласованные действия и показывает
последствия исходной идеи: общие Repository в разных Projects, сохранение
завершённой работы, разные смыслы review и CI, ограничения данных и переход
к первоисточнику. Значимые агентские предложения и будущие возможности
помечены; конкретные технические схемы для чтения не требуются. По этим
признакам первый продуктовый проход **готов к обсуждению**.

Остаются вопросы, которые нельзя выдать за выбранный смысл: что именно
означает готовность открытого PR и как определить ожидание ответа; также
потребует проверки полезность предложенных сигналов. Это оценка автора
черновика, не согласование всей спецификации владельцем и не доказательство,
что каждая техническая ветвь готова к реализации.
