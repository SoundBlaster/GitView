# GitView: продуктовая проекция первого прохода

Рабочий черновик на основе [исходного намерения](../../.specgraph/root_intent.md),
[обсуждения продукта](../product-discovery.md), [корневой спецификации](GITVIEW-SPEC-0001.yaml)
и сохранённых предложений. Он показывает, что пользователь делает и что
должно оставаться понятным, не выбирая окончательный способ реализации.
Согласованные решения и агентские рабочие уточнения различаются ниже.

## Зачем

GitView — компактный личный обзор GitHub для человека, у которого много
репозиториев и работы, в том числе созданной coding agents. Он помогает
увидеть текущие PR и Issue, завершение работы и места, требующие внимания.
Из объекта можно перейти к первоисточнику на GitHub; GitView не должен
заменять весь GitHub.

## Что объединяет обзор

- **Project** GitView содержит один или несколько GitHub Repository. Один
  Repository может входить в разные Projects; по умолчанию один Project
  соответствует одному Repository. Organizations — метаданные источника,
  и внутри Project могут быть Repository разных организаций.
- У Project есть собственные имя, необязательное описание и состав. Имя или
  текущий адрес Repository не определяют его идентичность: подтверждённые
  rename и transfer сохраняют тот же Repository и его участие в Projects.
  Если прежний адрес занял другой Repository, его история и состав не
  объединяются со старым; временная недоступность сама по себе не означает
  удаление.
- PR и Issue — разные объекты источника. Их связь не доказывает мотив актора
  и не превращает пару автоматически в две независимые задачи.

Основание: [правила Project](project-summary-proposal.md),
[identity Repository](GITVIEW-SPEC-0002.yaml),
[предметная модель](../../ontology/domain-model.md).

## Как появляются Projects

Пользователь подключает GitHub и выбирает доступные репозитории. После
подтверждения для них появляются Projects по правилу «один к одному»;
пользователь может создать свой Project, объединить в нём репозитории,
переименовать его или изменить состав. При этом один Repository может
оставаться в нескольких Projects.

Удаление Repository из одного Project не удаляет его на GitHub и не меняет
другие Projects. У сохранённого Project должен остаться хотя бы один
Repository. Если GitView не может определить доступные репозитории, он не
должен говорить, что их точно нет. Конкретный способ подключения и изменения
состава — предмет дальнейшей проработки. См.
[0005](GITVIEW-SPEC-0005.yaml), [0019](GITVIEW-SPEC-0019.yaml).

## Как человек осматривает работу

1. На общем уровне видны Projects и их краткие показатели. При переходе к
   Project можно увидеть общую работу и выбрать отдельный Repository; для
   многорепозиторного Project доступен обзор состава. Для Project с одним
   Repository не нужен дублирующий промежуточный экран.
2. PR и Issue представлены масштабируемой сеткой в духе Photos. На плотном
   уровне можно увидеть много объектов; pinch меняет плотность и доступную
   детализацию. Плотность сама не меняет выбранный Project или фильтры.
3. Long press даёт preview выбранного объекта до открытия; должен быть
   доступный способ выполнить те же основные действия без этого жеста.
   Открытие объекта сохраняет контекст для возвращения. Исследовательский
   sliding preview и глубокий просмотр PR — отдельные будущие возможности.

Прямой вход в общую работу многорепозиторного Project и точная организация
перехода к его составу — рабочее уточнение агента; native gesture mechanics
и конкретные элементы интерфейса ещё не выбраны.
См. [0006](GITVIEW-SPEC-0006.yaml), [0074](GITVIEW-SPEC-0074.yaml),
[0015](GITVIEW-SPEC-0015.yaml).

## Что видно сегодня и при фильтрации

По умолчанию Today включает незавершённую работу, в том числе начатую ранее,
а также работу, закрытую или влитую сегодня. Завершённая карточка не
исчезает только потому, что изменила состояние. Явный фильтр может скрыть,
например, merged или closed. Новое состояние, незагруженная работа и
отсутствие результатов не должны выглядеть одинаково.

Счётчик или сигнал может открыть соответствующую выборку, сохраняя Project,
условие и контекст Repository. После обновления число в выборке может
измениться; это не должно незаметно менять смысл исходного показателя.
См. [0007](GITVIEW-SPEC-0007.yaml), [0092](GITVIEW-SPEC-0092.yaml).

## Что содержит объект

В обзоре PR доступны выбранные сведения об identity и тексте, состоянии и
контексте, review, счётчики CI, изменения и времена. Обзор Issue показывает
состояние, связанные объекты, участников, счётчики обсуждения и дочерних Issue
и времена. Не все сведения обязаны помещаться в маленькой карточке. Список
файлов diff, содержимое review threads и отдельные прогоны CI не входят в
согласованный минимальный состав. Доступен переход к исходному объекту и
лёгкий sharing.

CI, review и незакрытые треды — разные признаки. Плохой CI не означает
отклонённое review; закрытая Issue не обязательно означает выполненную работу.
[Выбор PR](pull-request-ontology-options.md), [выбор Issue](issue-ontology-options.md),
[обзор PR](GITVIEW-SPEC-0041.yaml), [обзор Issue](GITVIEW-SPEC-0039.yaml).

## Зачем структурированы описания

Для новых Issue и PR в участвующем процессе согласованы разделы: проблема,
мотивация, ожидаемый результат и ссылки; для PR дополнительно — изменения
и проверка. Это помогает быстро понять, **зачем** появилась работа и что
предлагается, особенно когда её создают агенты. Авторское описание остаётся
словами автора: оно само по себе не доказывает результат или успешный CI.

Существующие и внешние объекты с другим форматом всё равно доступны: их
исходный текст нельзя заменять выдуманными разделами. Формат обязателен в
выбранном процессе создания, но конкретный способ обеспечить это ещё
предстоит внедрить; наличие шаблона само по себе не гарантирует соблюдение.
См. [0010](GITVIEW-SPEC-0010.yaml).

## Сводка, история и внимание

Project показывает число Repository и доступность данных, открытую работу,
сигналы CI/review и блокировок, результаты за период и графики при наличии
истории. Например, три проблемных PR в двух Repository — это два разных
числа. Общий итог по нескольким Projects не должен дважды считать общий
Repository. Недостаток истории не изображается нулём.

«Что готово» для открытого PR и ожидание ответа требуют точного смысла.
Размер обсуждения и период без новых комментариев — отдельные рабочие
предложения агента; порог 24 часа не выбирался владельцем и не доказывает,
что кто-то обязан ответить. См. [0057](GITVIEW-SPEC-0057.yaml),
[0062](GITVIEW-SPEC-0062.yaml), [0097](GITVIEW-SPEC-0097.yaml).

## Данные и визуальный характер

Приложение хранит ранее полученные данные и может показать допустимый
последний результат при ошибке обновления, обозначив время и проблему.
Обновление доступно вручную; при открытии и в фоне оно выполняется по
возможности системы и источника. Неполные, устаревшие и недоступные данные
не представляются как точный актуальный ноль. Сетевая ошибка отличается
от подтверждённого отзыва доступа: после отзыва нельзя продолжать показывать
затронутые закрытые данные только потому, что они сохранены локально.

Направление интерфейса — нативный Apple Look, системные цвета, SF Symbols и
Liquid Glass с минимумом декоративных компонентов. Требования тестируемости,
DI, TDD и сетевых/data mocks сохранены как ожидаемые качества разработки.
Выбор конкретного хранилища, GraphQL-операций, типов и UIKit/SwiftUI-механик
не является продуктовым результатом сам по себе.

## Критерий первого автономного прохода

Первый проход можно считать содержательно готовым к обсуждению, когда
пользователь узнаёт свою идею в связанных маршрутах и видит продуктовые
последствия, различия состояний и открытые вопросы; неясные места явно
помечены, а не незаметно решены как якобы утверждённые. Число узлов и
`checked` не являются этим критерием.

Более детальная стадия может доводить выбранные ветви до достаточности для
реализации и проверки. Существующие технические спецификации и исследования
сохранены для неё; их объём, точные схемы и выбранные агентом механизмы не
должны становиться скрытым условием завершения первого продуктового прохода.
