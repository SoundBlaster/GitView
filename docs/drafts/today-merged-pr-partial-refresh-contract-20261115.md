# GitView: merge в Today и неполное обновление

Рабочий контракт для review на основе GitView
`90cd790179df0efda05a08c781c5d56219e90150`; правки к четырём указанным ниже
узлам снимают безусловное предположение о локальном дне. Это спецификация
одного пути, не выполненный GitHub-запрос, тест приложения или разрешение
имплементации всей области. Она адресует первый пункт
[оставшихся работ](stopping-criteria-audit-20261115.md#оставшиеся-блокирующие-работы),
не закрывая его целиком.

## Контекст и входы

Пусть пользователь открыл Project P, а его подтверждённый состав включает
Repository R. Выбран динамический Today с захваченным интервалом I и без
ограничения lifecycle или иного фильтра, требующего неизвестное текущее
состояние PR. Подтверждённый состав P на T1 и T2 одинаков и включает R.
I — интервал выбранной политики;
день устройства является одним из предложений, а не предусловием этого примера.
PR X имеет подтверждённые source instance, тип PR, identity и привязку к R;
одноимённый или однономерный объект сам по себе не равен X. Для показа
необходима применимая разрешающая политика раскрытия, учитывающая текущие
локально установленные ограничения. Происхождение, scope и время каждого
факта сохраняются отдельно.

На T1 пригодное source-наблюдение подтверждает для X `state=MERGED`,
`mergedAt=M`, причём M входит в I; title и локальный номер доступны и
разрешены. Для примера предположим, что **независимые свидетельства**, включая
охват применимых альтернатив Today, подтверждают полную выборку P в её
указанном scope и reference T1. Тогда суммарное число distinct PR в merged
категории равно N, включая X. Полнота — дополнительное предусловие, не
следствие успешного одного запроса или числа вернувшихся карточек.

На T2 тот же Project и интервал остаются активными, новое обновление
запрошенных частей PR оказывается неполным: возможны ошибки отдельных полей,
недоступная страница или прерванный обход. Вариант A: X вообще отсутствует в
частичном ответе, включая случай, когда ошибка non-null `state` привела к
обнулению узла X или вышестоящего nullable поддерева. Вариант B: X, title и
`state` получены, но nullable `mergedAt` затронут ошибкой или не запрошен.
Если поле не запрошено, это отдельная форма операции, не утверждение о двух
выбранных запросах, которые оба запрашивают `state` и `mergedAt`.
Отдельно предположим, что известного
изменения доступа, достоверного удаления, противоречащего факта или изменения
фильтра нет. Эта оговорка не утверждает, что удалённый доступ не мог измениться
без наблюдения приложения.

## Обмен и решение

1. **Source → нормализованный факт.** Выбранное рабочее направление 0102
   использует отдельно атрибутируемые open и recent PR portions; пример
   [recent PR](today-graphql-operation-candidates-20261115.md#recent-pr-candidates)
   запрашивает typed Repository parent, PR `id`, `state`, `mergedAt` и
   отдельные поля. [0101](GITVIEW-SPEC-0101.yaml)
   `contract.graphql_fact_profile` и `graphql_lifecycle_mapping` связывают
   применимые поля с этим PR и различают время merge и время наблюдения.
   Успешная схема запроса не доказывает фактический grant, ответ GitHub или
   полноту популяции. Тип и Repository identity должны подтверждаться, а не
   выводиться только из адреса.
2. **Неполный ответ → domain input.** [0044](GITVIEW-SPEC-0044.yaml)
   `contract.field_evidence`, `field_refresh`, `partial` и
   [0116](GITVIEW-SPEC-0116.yaml) `contract.field_evidence`,
   `field_update_interpretation`, `graphql_discovery_exchange` сохраняют
   ошибку, конкретную область и отдельные времена. Отсутствие X в A не
   доказывает удаление или исчезновение merge; незапрошенное или ошибочное
   поле в B не является пустым, нулём или заменой значения T1. Title T2 не
   делает `mergedAt` или lifecycle наблюдением T2. Новые пригодные факты и
   ошибки могут сосуществовать с доступными фактами T1.
3. **Domain input → Today.** Если подтверждённое событие M всё ещё применимо
   к X, R и захваченному I, [0027](GITVIEW-SPEC-0027.yaml)
   `contract.base_inclusion`, `observed_event` и
   [0110](GITVIEW-SPEC-0110.yaml) `prepared_alternatives`, `applicability`
   дают подтверждённое совпадение по событию, даже если текущий lifecycle
   неизвестен. Это совпадение имеет собственный контекст: оно не доказывает,
   что GitHub был полностью прочитан на T2, или что все поля X актуальны.
   Если identity, допустимость, событие или граница I больше не подтверждены,
   результат оценивается по оставшимся данным и может быть неопределённым;
   совпадение не поддерживается одной лишь старой карточкой.
4. **Карточка и счётчик.** [0115](GITVIEW-SPEC-0115.yaml)
   `presented_result`, `selected_source_limitations` показывает разрешённый
   X и доступное ограничение T2 с временами отдельных фактов. Показывать
   текущую метку lifecycle можно лишь при применимом свидетельстве; иначе
   показать допустимое last-known значение с T1 или неизвестность, не
   переименовывая его в факт T2. Согласно [0057](GITVIEW-SPEC-0057.yaml)
   `today_breakdown_evidence` и [0110](GITVIEW-SPEC-0110.yaml)
   `collection_composition`, N может оставаться отдельно атрибутированным
   полным **прошлым** значением на T1, если сохраняются его scope, evidence и
   допустимость раскрытия; как точный текущий итог T2 оно не установлено.
   Разрешённое наблюдаемое подмножество можно показать с его неполным scope
   и временами, не объявляя его числом всех PR, актуальной нижней границей или
   количеством невидимых объектов. Если N не может быть безопасно раскрыто,
   показать только допустимое ограничение без раскрытия скрытого вклада.

Локальное сохранение и результат источника независимы: пригодный в текущем
сеансе X не становится заведомо восстановимым после перезапуска, пока его
сохранение не подтверждено. После рестарта используются только фактически
восстановленные и разрешённые evidence, а не один receipt. См. 0115
`source_and_storage_outcomes`, 0116 `retention_result_shape` и сценарий
`source_to_recovered_grid`.

## Когда результат меняется

- Если сменился I, оценить M относительно нового интервала; при этом другой
  подтверждённый критерий Today или явно выбранный исторический режим может
  поддержать показ X. Удаление карточки из Today не означает удаление PR.
- Если сохранённый состав P изменился, пересчитать применимый scope и его
  покрытие; не переносить прежнюю полноту на новый состав и не подменять X.
- Если источник установил применимое исправление события или identity, либо
  есть неупорядоченный конфликт, переоценить конкретный факт и его поддержку;
  не выбирать значение по одному времени получения. Подтверждённое удаление
  имеет собственные source semantics и не выводится из неполного списка.
- Известный применимый отказ или disconnect ограничивает приватные данные и
  раскрывающие числа до отдельно поддержанного восстановления. Неполный ответ
  не является новым grant. Что допустимо offline при неизвестном удалённом
  отзыве остаётся открытой продуктовой политикой 0036.
- Явный фильтр может исключить подтверждённый объект в своём scope. Для
  текущего lifecycle-фильтра неизвестное поле не становится ложным лишь из-за
  того, что merge был подтверждён ранее; наличие события и текущий state —
  разные основания.

## Оставшиеся ограничения этого маршрута

| Область | Что остаётся установить до соответствующего implementation-ready решения |
| --- | --- |
| Today | Продуктовый смысл интервала и часового пояса — 0049; пример не выбирает его. |
| Source | Применимость выбранных операций 0101–0102 и source-backed критерий полного объединения для разрешений, ошибок и изменяющейся пагинации; статическая проверка схемы не подтверждает live behavior. |
| Чтение и durable recovery | Выбранная реализация должна обеспечивать evidence и outcomes 0116/0126; конкретный provider, восстановимость и результаты реального рестарта не доказаны. |
| Доступ | Выбрать приватную offline-политику 0036 и определить применимые границы разрешений для используемого source; отсутствие известного denial не равно текущему grant. |
| UI и тест | Уточнить и проверить выбранное нативное представление частичности и сохранённого времени, а также TDD сценарии с doubles и последующее source/device evidence по 0115 и 0079. |

Этот набор — точная область одного примера. Он не определяет все поля PR,
общий Project breakdown, исторические графики или выпуск приложения.

## Независимое ревью уточнения

Ревьюер с отдельным контекстом сверил
`404e3fda1c6e9125a6a5c6781cf0ae747a2b1ef1` с контрактами отбора, покрытия и
наблюдений. Цель этого прохода — проверить, может ли исполнитель однозначно
вывести карточку и счётчик из полного и неполного обновления. Ниже записаны
замечания к этой ревизии и предложенные проверки после исправления.

| Замечание и адрес | Проверка исправления |
| --- | --- |
| Область отбора. Вход допускает активный фильтр `merged`, но вывод в «Domain input → Today» опирается только на событие merge. При неизвестном текущем state слой `0110.contract.filter_facets` может вернуть неопределённость. Совпадающий ID Project также допускает изменение его состава к T2. | Зафиксировать в основном примере применимый состав Project и Today без фильтра по текущему статусу. Отдельно проверить неизвестный фильтр и удаление R из Project до завершения обновления. |
| Граница Today. В примере используется захваченный интервал I. `0027.contract.scope_change`, `0049.contract.coverage_basis`, `0101.contract.graphql_close_evidence` и три соседних пункта `0110.contract.inputs`, `temporal_precision`, `input_evidence` ссылаются на локальный день без условия. | Передать захваченный интервал и правило его границ в вычисление. Сценарий со сменой дня устройства при неизменном I должен сохранять результат для прежнего интервала и области. |
| Форма ответа GraphQL. В обеих выбранных PR-операциях запрашиваются `state` и `mergedAt`. Ошибка исполнения поля `state: PullRequestState!` обнуляет объект PR или более широкий результат. Ошибка nullable `mergedAt` может сохранить `state` и `title`. | Проверить два отдельных примера ответа. В первом использовать сведения T1 после потери объекта из результата. Во втором учитывать успешно полученные поля T2 и основание для времени merge отдельно. [Правило распространения ошибок GraphQL](https://spec.graphql.org/September2025/#sec-Handling-Execution-Errors) |
| Событие закрытия. `0027.contract.base_inclusion` требует merge или закрытие без merge. В `0110.contract.prepared_alternatives` общее событие closure может быть принято за подтверждение этой альтернативы. `0102.contract.selected_outcome_evidence` передаёт `ClosedEvent`, который связывает объект и время закрытия. | Для старого PR с одним `ClosedEvent` и неизвестным merge явно определить, какого свидетельства достаточно для вывода о закрытии без merge. |
| Полнота счётчика. Число N для T1 требует покрытия применимых статусов, фильтров и доступа. Сценарий `0057.specification.scenarios.new_pr_after_breakdown` предполагает достаточное покрытие T2 и выводит точное 101 из старых 100 и одного нового PR. В этой предпосылке допускаются другие изменения состава или доступа. | Явно задать, что новый PR является единственным изменением, влияющим на итог 101. При частичном обновлении проверить отдельно атрибутированное прошлое число, наблюдаемое подмножество и случай, когда независимые данные устанавливают точный итог T2. |

Статус замечаний — открыты для автора маршрута. Повторное ревью проверяет
изменённые поля и сценарии после исправлений. Проверка была чтением
спецификаций и зафиксированной схемы GraphQL.

Продуктовая интерпретация Today, offline-доступ и source-backed способ
классифицировать конкретный PR close event остаются открытыми. Правки не
утверждают разрешения GitHub, результат API, реальную выдачу или факт
семантического принятия. Независимый повторный review ещё требуется.

Штатный runtime `3593bd75` проверил изменённые 0027, 0049, 0057, 0101,
0102, 0110, 0115 и 0116 командой `next-move -- --candidate-file <path>`:
каждый ответил `checked` с перечнем только `yaml_mapping`, `spec_kind`,
`file_id_match`. Это проверка формы файла, а не сценариев, логики GraphQL или
исправления замечаний. Например, тот же `checked` для 0110 не сообщает,
соответствует ли `pr_close_event_without_merge_classification` правилу 0027.
Результат команды не содержит решения reviewer и не связывает пять замечаний
с повторным независимым review. Нужны отдельное чтение reviewer на итоговой
ревизии и явные disposition; наличие локальных контрпримеров его не заменяет.
