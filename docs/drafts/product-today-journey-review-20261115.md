# Сверка сквозного сценария Today

Ручная продуктовая проверка по состоянию `5f2e527`, с добавлением одного
сценария в 0043 после сверки. Это не исполнение сценариев и не независимый
review всего графа. Рассмотрены конкретные acceptance и сценарии, указанные
ниже; полный текст каждой спецификации и все возможные маршруты не проверялись.

## Пользовательский путь

Пользователь открывает работу Project: Today включает незавершённые объекты и
подтверждённые события завершения за сегодня. Если 95 из 100 PR влиты, они
не исчезают по умолчанию. При желании пользователь исключает merged фильтром,
открывает нужный объект, возвращается и может отменить фильтр. Источник и
Project выбранного объекта остаются узнаваемыми.

| Участок | Проверенное основание | Граница вывода |
| --- | --- | --- |
| Завершение работы | Сценарии `work_completes` и `complete_multi_repository_today_journey` в [0043](GITVIEW-SPEC-0043.yaml), `dense_grid_keeps_completed_work_distinguishable` в [0093](GITVIEW-SPEC-0093.yaml). | Примеры предполагают подтверждённые наблюдения; они не устанавливают текущее состояние GitHub после неудачного обновления. Общий вход Project с несколькими Repository — кандидат. |
| Фильтр и возврат | `empty_lifecycle_then_reset` и `clear_signal_condition` в [0092](GITVIEW-SPEC-0092.yaml), `dense_grid_zoom_preview_round_trip` в 0043. | Очистка фильтра не меняет исходные данные и не делает исходный сигнал свойством всех появившихся объектов. Количество колонок адаптивно. |
| Неполные данные | `intentional_empty_and_failed_refresh` и `unfiltered_event_with_unknown_lifecycle` в [0110](GITVIEW-SPEC-0110.yaml); acceptance [0089](GITVIEW-SPEC-0089.yaml). | Намеренно пустая выборка не доказывает отсутствие работы; событие завершения и текущее состояние — разные факты. 0110 остаётся техническим кандидатом. |
| Смена дня и preview | Acceptance и `preview_at_boundary` в [0049](GITVIEW-SPEC-0049.yaml); acceptance [0093](GITVIEW-SPEC-0093.yaml). | Preview не подменяет объект при смене дня; локальный день устройства — кандидат, а не выбранный пользователем часовой пояс. |

Для связки этих условий добавлен `completed_work_filtered_during_refresh_failure`
в [0043](GITVIEW-SPEC-0043.yaml): после подтверждённого наблюдения повторное
обновление не удалось, пользователь фильтрует работу, просматривает объект и
снимает фильтр. Сценарий отдельно сохраняет время наблюдения и ограничение
покрытия: возврат карточек не выдаётся за новое получение с GitHub. Это
планируемое поведение, а не результат теста.

## Что по-прежнему открыто

Эта сверка поддерживает обсуждение пути сверху вниз, но не устанавливает
готовность ветви к реализации. Смысл общей категории «готово», границы дня,
прямой вход в работу нескольких Repository и конкретные native-переходы
остаются вопросами или предложениями из
[карты решений](product-open-decisions-20261115.md). Отдельно нужны проверка
доступности исходных данных GitHub и свидетельства работы на платформе.

Следующая полезная сверка — путь от сводки CI или review к отфильтрованной
работе: проверить единицы счётчиков, частичное покрытие и то, что изменение
фильтра не приписывает всем результатам исходное состояние сигнала.

владелец эту политику ещё не выбрал. Без такого выбора нельзя объявить конкретное
поведение приватного cache готовым к выпуску. Технические кандидаты хранения не
доказывают надёжность восстановления или возможность обнаружить каждый откат.

## Состав Project и общий Repository

На базе `d79efbb` сверены acceptance [0005](GITVIEW-SPEC-0005.yaml),

подтверждение сохранения данных или native-навигации.

| Ситуация | Рассмотренный результат | Ограничение |
| --- | --- | --- |
| Repository R в Projects P и Q | `shared_repository` в 0025 и 0043: удаление членства в P не меняет Q и источник; общий уникальный итог не считает R дважды. | Членство в каждом Project и уникальный итог портфеля — разные области подсчёта. |
| К Project добавлен Repository | `single_project_gains_member` в 0091 и `single_project_expands_while_open` в 0043 сохраняют контекст и показывают неполное покрытие новых данных. | Прямой вход в общую работу Project — кандидат; неизвестное содержимое нового Repository не равно пустому. |
| Убран Repository открытой карточки | `replace_sole_member_with_object_open` в 0091 сохраняет разрешённый preview до закрытия, затем пересчитывает Project по новому составу. | Если открыта отдельная область удалённого Repository, её не подменяют другим Repository или Project. Ограничение доступа применяется отдельно. |
| Конфликт двух правок | `name_conflict` в 0083 различает сохранённое значение и ожидаемое намерение, не выбирая за пользователя. | Повторное сохранение требует проверки актуального состава и допустимости; проектный default-association — отдельный кандидат. |

Уточнён acceptance в 0083: поле имени сохраняется, но проверка непустого имени
условна, как и в `specification.contract.revalidation` этого же узла и
`name_policy` в 0111. Ранее выражение «remains named» могло ошибочно читаться
как уже принятое требование непустого имени. Сценарии о default association и
создании отдельного custom Project не превращают эти варианты в решение
владельца; пользовательское правило членства в нескольких Projects от них не
зависит.
