# GitView — product clarification review

Ручной pilot для вопроса: **достаточно ли связно первый проход раскрывает
продуктовую идею и её последствия, чтобы обсуждать её с владельцем?**
Проверяемый снимок GitView: `5f14c705c7fbe04f7dfb6030c2cd29b9a5e59892`.
Критерии взяты из [0127](GITVIEW-SPEC-0127.yaml) и обсуждения; это не
общепринятый профиль PRR и не автоматическая проверка SpecGraph.

Здесь `описано` означает, что соответствующая мысль найдена в черновике;
`открыто` — существенный выбор или смысл виден, но не установлен;
`не проверено` — для заключения нет соответствующего evidence;
`вне области` — критерий не относится к этому вопросу. Это не единый балл.

| Критерий | Результат и основание | Граница / следующее уточнение |
| --- | --- | --- |
| Зачем нужен продукт и что он не обязан заменять | **Описано:** [0001](GITVIEW-SPEC-0001.yaml), [проекция](product-first-pass-20261115.md): компактный обзор GitHub и переход к источнику. | Полезность ещё не подтверждена работающим приложением. |
| Как организуется работа | **Описано:** [0005](GITVIEW-SPEC-0005.yaml): Project с одним или несколькими Repository, общий Repository в разных Projects и организации как независимый контекст. | Детали создания, имени и default association — кандидаты; [карта решений](product-open-decisions-20261115.md). |
| Как человек осматривает и фильтрует работу | **Описано:** [0007](GITVIEW-SPEC-0007.yaml), [0015](GITVIEW-SPEC-0015.yaml), проекция: Today сохраняет незавершённое и завершённое сегодня; плотность, preview, открытие и возврат различаются. | Переход между scope через pinch и дальнейший sliding preview остаются отдельными вопросами; native поведение не проверено. |
| Что означают состояние и внимание | **Описано с открытым смыслом:** [0057](GITVIEW-SPEC-0057.yaml), [0125](GITVIEW-SPEC-0125.yaml) различают lifecycle, review, треды и CI. | Что именно называть «готово» и кто должен ответить — **открыто**; известный сигнал сам по себе не доказывает merge eligibility. |
| Данные, ошибки и доверие к прошлому | **Описано с открытым выбором:** [0036](GITVIEW-SPEC-0036.yaml), [0048](GITVIEW-SPEC-0048.yaml), [0064](GITVIEW-SPEC-0064.yaml): last-known данные и неполнота отличаются от актуального нуля; история текущего состава не доказывает прежний состав. | Политика приватного offline после потерянного отзыва и перспектива исторического состава — **открыты**. |
| Форматы и граница оригинала | **Описано:** [0010](GITVIEW-SPEC-0010.yaml), [0016](GITVIEW-SPEC-0016.yaml): нужные разделы для участвующего процесса и сохранение чужого исходного текста; источник можно открыть. | Enforcement не установлен; состав sharing payload остаётся предложением. |
| Выборы реализации и запрошенное качество разработки | **Описано:** [0127](GITVIEW-SPEC-0127.yaml) сохраняет DI, TDD, testability и mocks; продуктовая проекция не требует конкретной базы, API или UI control для понимания идеи. | Реальное применение библиотек, тесты и поддерживаемые платформы **не проверены**. |
| Производственная эксплуатация и фактический launch | **Вне области** этого product clarification review. | Для последующего release/production review понадобятся отдельные применимые критерии и реальные evidence. |

**Рабочий вывод автора:** документ можно предложить для обсуждения продуктового
смысла; это не принятие владельцем каждого предложения и не допуск к коду или
запуску. Основания — приведённые источники и предыдущий
[независимый обзор](independent-product-review-20261115.md) более раннего
снимка. Полная независимая проверка текущего состояния не проводилась.

Этот pilot намеренно фиксирует описание и открытые решения рядом. Незнание
точного порога, версии API или устройства не является автоматически провалом
этого профиля, но остаётся видимым для следующей стадии.

## Состояние знания и решение о переходе

Различие предложено владельцем в заметке Readiness Review: один и тот же
открытый вопрос может иметь разные последствия для разных переходов. Таблица
ниже — ручная иллюстрация для GitView, не утверждённая policy и не разрешение
на разработку или запуск.

| Вопрос и состояние знания | Уточнение идеи → интерактивный UX-прототип | Спецификация → реализация приложения |
| --- | --- | --- |
| Today сохраняет завершённую сегодня работу: **описано** в 0007. | Можно использовать это правило в исследовательском макете; такой макет не доказывает работу GitHub integration. | Само описание не устанавливает достаточность всех source mappings, состояний и тестовых границ для реализации. |
| Точный смысл «готово» для открытого PR: **открыто** в 0125. | Можно показать отдельные известные сигналы и явно помеченные варианты, не выдавая один за выбранный смысл. | Если выбранная ветвь обещает общий ярлык или фильтр «готово», её правило и применимость требуют дальнейшего решения. Остальные независимые функции не автоматически блокируются. |
| Приватный offline после потерянного отзыва: компромисс **открыт** в 0036. | Для макета с вымышленными данными можно показать варианты и не утверждать реальную безопасность. | Для реализации показа сохранённых приватных данных нужна отдельная применимая политика и проверка её границ; решение не следует выводить из одного наличия cache. |

На этом снимке автор может рекомендовать обсуждать или исследовать указанные
варианты, но **решение о переходе не вынесено**: ни эта таблица, ни факт
наличия evidence не создают полномочия на реализацию или принятие риска.
Правило, кто принимает решение и что допустимо для каждого перехода, в этом
pilot не формализовано. Ранее созданные примеры `described` и `open` описывают
только состояние знания; они не являются вердиктами о переходе.

### Влияние условных ветвей на граф

На снимке `1be405238de462d02312f7d6d8e033169d826847` проверены входящие
явные `depends_on` и `refines` для 0055 (fixed cohort), 0094 (возраст
комментария), 0120 (cross-scope pinch), 0114 (candidate credential protocol),
0117 (history clear) и 0125 (completion и optional review-stage filter).
У каждого из этих шести узлов входящих ссылок указанных двух типов не найдено.
При этом в тексте других specs есть ссылки на их условные сценарии; они не
являются проверенными графовыми рёбрами. Сам 0125 содержит и согласованную
видимость результатов, поэтому весь узел нельзя считать необязательным только
по наличию необязательного фильтра.

Это ограниченная проверка деклараций, а не вывод о фактической readiness policy
или всех смысловых зависимостях. Она не доказывает, что SpecGraph автоматически
не блокирует переход, и не отменяет отдельной проверки согласованных результатов
в родительских specs. Профиль принятия решения для выбранного перехода ещё не
реализован.

Для той же ограниченной проверки прочитаны acceptance родительских 0007,
0011–0015, 0019, 0036, 0062, 0066 и 0086. Согласованные результаты
представлены в них независимо от выбора fixed cohort, age proxy, cross-scope
pinch, GitHub App и history clear: это сохранение завершённой сегодня работы,
раздельные CI/review, понятные сводки и история при достаточном evidence,
изменение плотности и static preview, а также доступ и last-known данные.
Приватная offline policy в 0036 остаётся явно предложением; её открытый риск
нельзя считать автоматически разрешённым для реализации.

Это чтение acceptance перечисленных узлов, не формальная проверка их всех
зависимостей или полного текста каждого contract. Отсутствие обязательного
узла в `depends_on` также не доказывает отсутствие смыслового требования.

## Сверка с независимым обзором и автоматизацией

### Фактический пробный прогон: правило Today и открытый смысл готовности

На снимке Git `98f2c3c3ec10c4b7d30b7eb2e747f958a09a1ecd` установленный
runtime `3593bd75` вызван с `next-move --candidate-file` отдельно для 0007,
0125 и 0127. Все три результата вернули `checked`, `canonical: false` и
`next_action: review_candidate`; в каждом перечислены только `yaml_mapping`,
`spec_kind` и `file_id_match`. SHA-256 в результатах совпали с хешами файлов
на рабочем дереве. Для 0007 и 0125 они также совпали с закреплёнными хешами
в двух примерах ручного review выше.

| Критерий одной и той же стадии | Ручной вывод по тексту | Что установил вызванный инструмент |
| --- | --- | --- |
| В Today сохраняется работа, завершённая сегодня | **Описано:** acceptance 0007 предусматривает включение при подтверждённом результате и применимых scope/access. | Файл распознан как candidate и его ID соответствует имени; смысл и полнота исходных данных не проверены. |
| Установлено ли выбранное владельцем значение «готово» для открытого PR | **Открыто:** 0125 отделяет рабочий вариант агента от неустановленного общего смысла. | Тот же структурный результат `checked`; инструмент не установил выбор владельца или его отсутствие. |
| Какой критерий относится к первому проходу | **Описано:** 0127 определяет продуктовую ясность и явные неопределённости, оставляя технические решения на дальнейшее уточнение. | Структурный результат сам по себе не применяет этот критерий к 0007 или 0125 и не выдаёт решение о переходе. |

Таким образом, одинаковый `checked` совместим с разными состояниями знания.
Привязка хеша подтверждает, какой текст рассмотрен, а не то, что он
удовлетворяет намерению владельца. Это проверка трёх файлов одной командой,
не инвентаризация всех возможностей SpecGraph; решение о переходе и полномочия
не установлены этим прогоном.

Независимый обзор снимка `501c80f` также счёл первый проход достаточно
связным для обсуждения и выделил открытые вопросы готовности, истории и
приватного offline. Он дополнительно указал на риск чтения трёх агентских
предложений как принятых; соответствующие acceptance позже уточнены. Это
сопоставление разных снимков, а не повторное независимое подтверждение
текущего pilot или полного графа.

| Что можно автоматизировать | Что остаётся содержательным суждением |
| --- | --- |
| Проверить существование ссылки на spec и SHA-256 её снимка. | Действительно ли ссылка обосновывает конкретный вывод review. |
| Проверить YAML shape, ID, структуру зависимостей и наличие заданного поля. | Является ли описанное поведение полезным и достаточно ясным человеку. |
| Сопоставить явно указанный статус кандидата и декларации с конкретным критерием, если предусмотрен такой профиль. | Корректно ли атрибутирован выбор владельцу и нет ли противоречия в значении текста. |
| Показать найденные открытые вопросы и отсутствие подтверждённого evidence в определённой области поиска. | Какие неопределённости существенны именно для решения о следующем шаге. |

Последние два пункта — возможности для отдельного дизайна, а не утверждение,
что нынешний runtime умеет выполнять эти проверки полностью. В частности,
`next-move --candidate-file` проверяет mapping, kind и совпадение ID с именем
файла; он не устанавливает готовность продукта, качество суждения или
покрытие всего замысла. Результат автоматизации должен сохранять применимость,
источник и тип evidence, а не превращать отсутствие данных в `pass`.

## Сопоставление примеров с механизмами SpecGraph

[Пример `described`](product-review-example.yaml) и
[пример `open`](product-review-open-example.yaml) — проектные иллюстрации,
не запросы или отчёты поддерживаемого инструмента. В установленном runtime
`3593bd75` документ `evidence_provider.md` описывает адреса с revision,
spec ID, путём, pointer и digest, а также отдельные признаки полноты и
ограничения источника. Эти идеи подходят для точной привязки review к
прочитанным данным, но описанный там publication provider ограничен конкретным
профилем SpecGraph и сам не оценивает product readiness GitView.

`evidence_claim_admission.md` отдельно описывает `source_anchored`: он
подтверждает синтаксическую идентичность закреплённых источников и не запускает
тесты; `runtime_verified` имеет другой контракт доверия. Эти механизмы
не превращают авторскую оценку `described` или `open` в автоматически
установленный вердикт. Описанный admission требует определённых статусов и
Feature Passport inputs, которых текущие pre-canonical GitView drafts сами
по себе не предоставляют; применять его без этих оснований нельзя.

Для будущего review полезно исследовать reuse точных source locators,
hashes, scope и явных ограничений. При этом `open` здесь означает ручной
вывод по рассмотренным источникам, не доказательство отсутствия решения во
всей переписке. Новый общий формат или поддержка этих примеров инструментом
данной сверкой не объявляются.
