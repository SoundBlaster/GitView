# PullRequest: выбранный состав для дальнейшего уточнения

Статус: пользователь выбрал пункты из заготовки агента
(`conversation:gitview/excerpt-34`). Отмеченные пункты фиксируют состав для
дальнейшего уточнения. Это не утверждение всего sketch, готовая спецификация
приложения или изменение ontology package. Исходная заготовка сохранена в Git
и как отдельный источник агента в SpecDraft; ответ пользователя связан с ней.

Кандидатное значение: запрос на рассмотрение предлагаемых изменений кода и их
возможное включение в целевую ветку. Формулировка также требует выбора.

## A. Идентификация и описание

- [x] A1. Идентификатор в источнике и номер PR в контексте репозитория.
- [x] A2. Название.
- [x] A3. Описание / текст.
- [x] A4. Ссылка на первоисточник.

Дополнение пользователя (`excerpt-37`, согласование `excerpt-38`): обязательный
[формат описаний Issue и PR](github-templates/README.md). Описание PR A3 имеет
разделы `Problem`, `Motivation`, `Expected outcome`, `Changes`, `Validation`,
`References`. Согласованы разделы; правила извлечения текста и источников в
GitView уточняются в спецификации. `Validation` — заявление о проведённых
проверках, отдельно от получаемого из GitHub состояния CI.

## B. Состояние PR

- [x] B1. Жизненный цикл: открыт, закрыт без merge, merged.
- [x] B2. Признак draft отдельно от жизненного цикла.
- [x] B3. Метки / labels как дополнительные характеристики.

B1 — выбранный набор состояний по GitHub; это ещё не полная state machine переходов,
команд, условий и акторов. Draft не образует с review и CI одну общую шкалу.

## C. Контекст и участники

- [x] C1. Целевой GitHubRepository.
- [x] C2. Исходная и целевая ветки, ссылка на текущую ревизию изменений.
- [x] C3. Автор / создатель PR как роль участника.
- [x] C4. Запрошенные reviewers.
- [x] C5. Связанные Issue.

Это выбранные ссылки и роли, а не только скалярные поля или объявленные типы отношений
в пользовательском смысле Ontology. Их происхождение через действия надо
рассматривать отдельно. Автор PR не автоматически User приложения или coding
agent. Ссылка на Issue сама по себе не устанавливает мотив актора. Названия
веток и технических ссылок не вводят новые ontology entities автоматически.

## D. Review

- [x] D1. Доступная итоговая оценка review со смыслом, заданным источником.
- [ ] D2. Связанные ReviewThread — не выбраны для текущего состава.
- [x] D3. Число тредов и число незакрытых тредов как отдельные метрики.

Отсутствие доступной оценки, отсутствие reviews и требование review различаются.
Итоговая оценка не заменяет счётчики тредов. Отдельные треды и их содержимое
в текущий состав не входят; это не удаляет сам термин ReviewThread из словаря.

## E. CI — только счётчики

- [x] Число красных.
- [x] Число жёлтых.
- [x] Число зелёных.
- [x] Общее число.

Пример пользователя: **красные / жёлтые / зелёные / всего = 3 / 4 / 8 / 15**.
Этот выбор заменяет исходные E1–E4; просмотр отдельных прогонов и результатов
не включён в текущий состав. Цвета здесь — согласованные обозначения счётчиков,
а не новые сущности или исчерпывающий enum исходных состояний GitHub.

Следующее уточнение пользователя (`conversation:gitview/excerpt-35-reply`):
ориентироваться на поведение самого GitHub. Считаем **актуальные отдельные
проверки PR**, по образцу списка проверок GitHub; это не число workflow runs
и не накопленная история попыток. При повторном запуске ориентируемся на
актуальное состояние проверки, не складывая прежнюю ошибку с новым успехом.

Точные правила выбора относящейся к PR ревизии и актуального результата при
повторных запусках, состав источников проверок и соответствие состояний цветам
надо сверить с GitHub в спецификации. В частности, пока не определено отображение
отменённых, пропущенных и нейтральных результатов. Ориентир согласован;
эквивалентность поведения GitHub ещё не проверена. Пример не устанавливает
правило, что сумма трёх цветов всегда равна общему числу. Недоступные данные
не равны нулю.

## F. Объём предлагаемых изменений

- [x] F1. Число добавленных и удалённых строк отдельно.
- [x] F2. Число изменённых файлов.
- [x] F3. Число коммитов.

Только счётчики; просмотр отдельных файлов, коммитов и diff этим выбором не
добавляется. Это измерения с конкретной областью подсчёта, а не стадии
жизненного цикла PR.

## G. Время

- [x] G1. Время создания и последнего обновления.
- [x] G2. Время закрытия или merge, когда применимо.
- [x] G3. Время получения наблюдения и его источник.

Времена предметных событий отличаются от времени наблюдения GitView. Точный
состав достаточного состояния и способ представления неполных данных открыты;
эту заготовку нельзя считать полным eventcore:StateSnapshot.

## Граница следующего шага

Далее уточняем смысл, типы значений, роли, допустимые состояния и
неизвестность для выбранных пунктов. Отдельно спецификации GitView определят
получение, обновление, вычисление и показ этих данных. «Готов к merge»,
«застрял» и «требует внимания» требуют собственных правил и пока не объявлены
исходными состояниями PR. Реализация просмотра внутреннего diff не предлагается.

Источник для сверки GitHub lifecycle / draft / review:
[GitHub GraphQL: Pull requests](https://docs.github.com/en/graphql/reference/pulls).
Остальная группировка — предложение агента на основе беседы, а не перенос
API-схемы в онтологию. Запрос пользователя: conversation:gitview/excerpt-33;
выбор: conversation:gitview/excerpt-34; ориентир CI:
conversation:gitview/excerpt-35-proposal и excerpt-35-reply.
Ссылки на excerpt обозначают локальные
фрагменты беседы, а не удостоверенные ID сообщений.
