# Выбор authorization flow: продуктовые требования и ограничения

Это предварительное решение для развития графа, а не регистрация приложения,
реальная авторизация или готовая к реализации архитектура. Основание — личный
нативный GitView, один активный GitHub identity в первом срезе, несколько
репозиториев из разных организаций, обзор без мутаций исходных PR/Issue и
необходимость работать с ранее сохранёнными наблюдениями.
Сравнение ниже — исторический срез до выбора кандидата 0098; актуальный
рабочий выбор и его границы изложены в последнем разделе.

## Решения, которые можно выразить сейчас

1. Оператор понимает источник, цель и существенный объём запрашиваемого
   доступа, может отменить вход и позже восстановить подключение.
2. Фактические capabilities grant проверяются отдельно от того, какие операции
   GitView намерен выполнять. Минимизация privileges — критерий выбора; более
   широкий grant нельзя называть read-only без оговорки.
3. User authorization, установка приложения и доступ к отдельным организациям
   и репозиториям — разные подтверждаемые факты. Неполная область доступа не
   делает организацию пустой и не удаляет Project.
4. Native binary — public client; встроенный client secret нельзя считать
   конфиденциальным. GitHub App installation private key не поставляется в app.
5. Никакой собственный backend пока не выбран. Если вариант его требует,
   необходимо определить его роль, владельца, доступ к данным и credentials,
   доступность и восстановление.

## Сравнение направлений

| Вариант | Сильная сторона | Нерешённое для GitView |
| --- | --- | --- |
| GitHub App, user authorization | Fine-grained permissions и выбор repository scope соответствуют цели ограниченного доступа. | Проверить покрытие выбранных полей, installation/approval в организациях и архитектуру обмена для public client; наличие установок не доказывает полный discovery. |
| OAuth App | GitHub документирует user authorization и совместимые потоки. | `repo` предоставляет значительно более широкий read/write доступ; для private данных нельзя называть такой grant read-only. Нужно отдельное обоснование и ясное disclosure, если он рассматривается. |
| Device flow | Документирован GitHub и может работать без client secret в конкретном обмене. | GitHub рекомендует применять его по обоснованной причине и отмечает риск phishing; у iPhone есть браузер. Нельзя выбирать этот вариант только потому, что он кажется проще. |
| Другой путь или дополнительный сервис | Может удовлетворить отдельным ограничениям. | Требует source-supported модели доступа, UX и явной границы доверия. Ручной ввод персонального токена не установлен как требование обычного пользовательского входа. |

Рабочая рекомендация — **исследовать GitHub App на behalf of user первой**,
не считать её уже выбранной. Согласно документации, GitHub App user token
ограничен правами пользователя, приложения и соответствующих установок.
Установка и user authorization — отдельные шаги; organization policy может
требовать отдельного одобрения. Это ограничивает грант и одновременно может
означать неполную видимость доступных человеку репозиториев.

Для GitHub App authorization-code обмена GitHub указывает client secret как
обязательный параметр. В руководстве для public clients GitHub одновременно
рекомендует PKCE и прямо признаёт, что embedded client secret невозможно
сохранить в тайне. Поэтому PKCE нельзя описывать как секретный storage или как
доказательство существования secretless token exchange. Обработка client secret
в рамках актуальной политики GitHub и threat model, а также необходимость
отдельного confidential участника остаются решениями для проверки.

## Что остаётся до выбора

- Сопоставить каждую первую продуктовую категорию данных с поддерживаемыми
  permissions и полями выбранной схемы; отдельно проверить доступ к разным
  организациям и последствия отсутствующей установки.
- Проверить актуальный native authorization, callback и обмен токена, а также
  expiry/rotation и восстановление из 0058/0085/0086 с учётом выбранной
  архитектуры. Не приравнивать документацию, mocks и реальное устройство.
- Явно решить, достаточно ли public-client модели или требуется сервис; если
  второй вариант, описать владельца, секреты, источник данных, доступность и
  privacy. Выбор остаётся открытым, а не скрытым системным обязательством.
- Проверить UX согласия и доступности; это не требует заранее выбирать лимиты
  запросов или детали реализации всех API.

## Рабочий выбор для первой версии

Позднее [0098](GITVIEW-SPEC-0098.yaml) предложил GitHub App user access token,
authorization code с S256 PKCE и системную browser authentication session без
отдельного backend GitView. GitHub [рекомендует PKCE для public clients](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)
и указывает, что встроенный `client_secret` невозможно сохранить секретным.
Он не используется как доказательство подлинности экземпляра приложения;
installation private key в приложение не помещается. Это выбор агента для
развития спецификации, а не создание регистрации или утверждение безопасности
реальной интеграции.

Для истекающих user tokens GitHub [описывает rotation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens):
успешное применение refresh token делает прежнюю пару недействительной. Если
ответ потерян либо новая пара не сохранена, локальный rollback не доказывает
восстановление доступа. 0098 задаёт координацию renewal и путь повторной
авторизации; сохранённые Projects при этом не удаляются. Фактические callback,
permissions, secure storage и UX всё ещё требуют проектирования и проверки.
