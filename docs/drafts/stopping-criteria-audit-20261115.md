# GitView: критерий остановки и проверка графа

Рабочая авторская проверка на Git commit `cefadab`, 15 ноября 2026. Цель — завершить спецификационную работу и не превращать возможные будущие уточнения в бесконечные обязательства. Это не независимое semantic review, не выполненные тесты продукта и не разрешение начать разработку до устранения указанных блокирующих пробелов.

## Критерий остановки

Граф готов к реализации, когда все пять условий одновременно выполняются:

1. Согласованные пользовательские маршруты и выбранные данные первой версии имеют прослеживаемые требования и проверяемые ожидаемые результаты.
2. Продуктовые родители, применимые уточнения и предметная терминология согласованы; неясный или отсутствующий термин не вводится незаметно. Достаточность ontology оценивается по используемым понятиям и действиям, не по количеству классов.
3. Для каждого конечного обязательства выбранного объёма определены область, входы, результаты, ошибки и неопределённость, зависимости и способ проверки, достаточные разработчику в контексте родителей. Структурный лист не обязательно является модулем; приёмочные и общие правила проверяются в контексте применимых реализаций.
4. Влияющие на результат или приёмку развилки имеют согласованное рабочее решение; невыбранные возможности явно условны или отложены. Детали, не меняющие контракт, не блокируют готовность.
5. Выполнены структурные проверки графа и предметная сверка ключевых сквозных сценариев с исходными решениями. Диагностика и её границы записаны; `checked` не заменяет такую сверку.

После выполнения этих условий новые сценарии добавляются, только если выявляют противоречие, меняют ожидаемый результат или нужны для проверки согласованного требования. Альтернативные UX-идеи, оптимизация, точные API budgets и теоретические аварии не возобновляют декомпозицию сами по себе. Реальные проверки GitHub, iOS, устройства и persistent storage выполняются по плану после появления реализации; они не могут быть предъявлены как уже выполненные.

## Оставшиеся блокирующие работы

1. **Минимальный сквозной source → Today → экран.** Выбрать и связать source operations и их смысл для открытия, созданных и завершённых за день PR/Issue, идентичности и выбранных полей; определить операцию → данные → coverage/error → domain input → видимое состояние, а также необходимый permission profile. Не требуется заранее выбирать численные лимиты; неподтверждённые возможности должны иметь честный fallback. Основные узлы: 0100–0102, 0110, 0115–0116.
2. **Хранение и Project setup.** Выбрать минимальную модель локальных сохранений и их восстановимого исхода, достаточную для Project, кэша и выбранных исторических данных; отдельно решить, действительно ли обязателен подробный durable batch/default-association протокол. Установить границы взаимодействия source, storage и решения, не требуя конкретного SQL или миграций ради самих спецификаций. Основные узлы: 0025, 0045, 0052, 0104, 0113, 0122–0124, 0126.
3. **Выбранные метрики и signals.** Для каждой обязательной метрики зафиксировать единицу, область, выбранное source evidence, unknown и маршрут к объектам. Для длинного review выбрать точное полезное значение либо явно ограничить первую версию согласованным способом; не называть объём обсуждения его длительностью. Узлы: 0057, 0061–0063, 0069, 0077–0078, 0097.
4. **Внешний формат Issue/PR.** Описать применимость и проверяемый механизм обязательных разделов к выбранным путям создания, включая ответственность и исключения; не выдавать template за enforcement. Фактическое изменение внешних repositories и получение permissions вне данного спецификационного прохода. Узел 0090.
5. **Финальная сверка реализационных листьев и терминологии.** После решений выше пройти каждый относящийся к текущему объёму конечный контракт с родителями и проверить вход/выход, ошибки, acceptance и ontology; отдельно отметить cross-cutting и отложенные листья. В частности, 0018 — будущее направление, 0055, 0094, 0120, 0125 и history clear — условные возможности; не считать их блокерами только из-за существования узла.

Новый пункт добавляется только при обнаружении отсутствующего согласованного требования или доказанного противоречия.
