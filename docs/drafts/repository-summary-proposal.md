# GitHubRepository: предложение сводки

Статус: предложение агента по запросу «Ок, хорошо. Сделай предложение»
(`conversation:gitview/excerpt-39`). Блоки и правила ниже ещё не выбраны.
Основа — согласованные поля PR и Issue и форматы описаний. Это проектирование
представления и вычислений для спецификаций; новая ontology entity «Сводка»
автоматически не вводится, определение Repository не меняется.

Задача: на любом масштабе видеть, сколько открытой работы есть, где нужно
внимание и какие результаты появились. Все числа относятся к определённому
GitHubRepository; текущее состояние отделено от результатов за период.

## A. Контекст и актуальность

- [ ] A1. Имя репозитория с owner, ссылка на GitHub.
- [ ] A2. Время наблюдения и полнота данных отдельно для PR, Issue и CI.

Название и owner не заменяют устойчивую идентичность источника. При частично
доступных данных показываем известное количество с признаком неполноты, либо
неизвестное значение, а не уверенный ноль. Один общий timestamp не должен
скрывать, что CI обновлён позже или раньше списка PR.

## B. Открытая работа сейчас

- [ ] B1. Всего открытых PR; из них draft.
- [ ] B2. Всего открытых Issue.

Draft — подмножество открытых PR. Открытые Issue и PR считаются отдельно:
связанная пара не означает две независимые задачи, поэтому сумму не называем
«объёмом работы». Подсчёт относится к полному выбранному набору объектов, а
не только к видимым карточкам на экране.

## C. Сигналы внимания сейчас

- [ ] C1. Число открытых PR с хотя бы одной красной актуальной проверкой.
- [ ] C2. Число открытых PR, для которых источник сообщает требование review.
- [ ] C3. Число открытых PR с итоговой оценкой review «запрошены изменения».
- [ ] C4. Число незакрытых review threads и число открытых PR с такими тредами.
- [ ] C5. Число открытых Issue с открытыми блокирующими Issue по явным связям.

Пример C1: два PR с пятью упавшими проверками дают «2 PR с красным CI», а не
«5 проблемных PR». Внутри PR остаются согласованные счётчики отдельных проверок.
Сырые счётчики проверок можно агрегировать отдельно, если это окажется полезно.

Категории пересекаются: один PR может одновременно иметь красный CI,
запрошенные изменения и незакрытые треды. Их нельзя складывать в общее число
проблемных PR. Для такого числа потребуется объединение по идентичности PR.
Наличие связанного blocker без актуального состояния не объявляет Issue
доказанно заблокированной. Запрос review сам по себе не означает ожидание
review от владельца GitView: личный фильтр потребует отдельного сопоставления.

«Давно нет ответа», «застрял» и «заброшен» пока не входят в базовую сводку:
нужны определения ожидания, релевантного события и временных порогов.

## D. Кандидаты на рассмотрение merge

- [ ] D1. Число открытых non-draft PR, для которых известные данные подтверждают
  успешную сводку актуальных проверок, одобрение review и ноль незакрытых тредов.

Предлагаемая подпись — «Проверки и review пройдены». Это предварительное правило
выборки для внимания пользователя, не исходное состояние PR и не гарантия
возможности merge. Неизвестные или устаревшие данные не подтверждают условие.
Отсутствие проверок и отсутствие требования review не считаем автоматически
прохождением: их трактовку надо согласовать отдельно. Точные правила состояний
CI и review должны следовать выбранному ориентиру на GitHub.

Конфликты и остальные условия возможности merge не входят в согласованный
набор полей. Поэтому сейчас не обещаем категорию «Готов к merge».

## E. Результаты за период

- [ ] E1. Число merged PR за выбранный период.
- [ ] E2. Число Issue, закрытых как completed за период.
- [ ] E3. Другие закрытия Issue отдельно по причине, включая неизвестную.

Предложение периода по умолчанию: последние 7 дней; варианты — 24 часа и 30 дней.
Это скользящие интервалы, не календарные недели/месяцы. Результаты не суммируются
в «выполненные задачи»: PR и связанная Issue могут описывать одну работу.

Для закрытий Issue нужно учитывать повторные открытия и закрытия. Если источник
даёт только текущее состояние и время последнего закрытия, нельзя выдавать это
за полную историю событий. Определение исторического подсчёта — отдельная
спецификация; отсутствие нужной истории остаётся видимым.

## F. Графики

- [ ] F1. По дням: merged PR и completed Issue двумя отдельными рядами.
- [ ] F2. Число открытых PR и Issue во времени двумя отдельными рядами.

Для F1 нужна подтверждённая история соответствующих событий. Для F2 нужны
сохранённые наблюдения или достаточная история изменений состояния: текущий
список объектов не доказывает значения прошлых дней. Пропуски не заполняются
нулём. Объём строк и коммитов пока оставляем в метриках PR: сумма размеров
нескольких PR может повторно учитывать один и тот же код.

## Как это проявляется в сетке — предложение UX

На дальнем масштабе: имя репозитория, открытые PR / Issue, число PR с красным
CI и признак актуальности. При приближении появляются остальные сигналы,
результаты за выбранный период и график. Выбор счётчика открывает соответствующую
выборку объектов; из объекта можно перейти на GitHub. Это ещё не утверждённая
навигационная спецификация. Визуальные компоненты остаются системными.

Иллюстративный пример, не реальные данные:

```text
SpecGraph
PR 8 · draft 2 · Issue 12

2 PR с красным CI · 3 ожидают review
7 незакрытых тредов в 3 PR
1 PR: проверки и review пройдены

За 7 дней: merged PR 14 · completed Issue 9
```

Один цвет «здоровья» всего репозитория пока не предлагается: он скрыл бы
количество, причины и неизвестность. Цвет сопровождает конкретный сигнал.

Для сводки Project используем уникальные репозитории в его составе. При общем
обзоре нескольких проектов репозиторий, состоящий в нескольких из них, не должен
дублировать общий итог. Объединение и правила агрегации Project пока не выбраны.

## Следующее решение

Выбрать блоки A–F и отдельно решить, нужна ли осторожная выборка D уже сейчас.
Затем зафиксировать области подсчёта, источники, свежесть и правила фильтрации
в ограниченной спецификации. Политики «готов», «застрял» и общий score не
вводятся молча. Все блоки выше остаются предложениями до выбора пользователя.
