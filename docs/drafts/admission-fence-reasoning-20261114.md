# GitView: порядок допуска и изменения доступа

Это разбор предлагаемого контракта [0113](GITVIEW-SPEC-0113.yaml), не
реализация и не доказательство поведения SQLite, Keychain или iOS.

Для одной подтверждённой batch selection различаются три границы: **локальный
допуск записи**, **наблюдение изменения доступа в работающем процессе** и
**подтверждённая запись fence**. Тап, создание asynchronous task и приход
ответа не являются взаимозаменяемыми границами. Запись Repository в Project и
operation receipt фиксируются одной транзакцией после проверки действующих
generation и batch status. Эта проверка не доказывает, что GitHub не отозвал
доступ незаметно для приложения.

| Порядок | Следствие |
| --- | --- |
| Допуск A → наблюдение denial → commit A | Уже допущенная локальная операция может завершиться; private content ограничивается немедленно и результат не восстанавливает доступ. |
| Подтверждённый fence denial → попытка допуска A | Старое свидетельство A не допускает новую запись. |
| Наблюдение denial → fence недоступен → попытка допуска A | В работающем процессе доступ и новый допуск блокируются; durability события неизвестна, требуется восстановление. |
| Подтверждённая отмена batch → старая отложенная попытка | Старое чтение активной batch не даёт начать entry. Результат уже допущенных entry выясняется отдельно. |
| Доступ B установлен в Keychain, но fence B не подтверждён | Нельзя считать, что смена аккаунта атомарно завершена в обеих системах; новая запись ожидает восстановления связки. |

Серьёзная незакрытая граница: процесс может завершиться после того, как
denial стал известен только в памяти, но до сохранения fence. На следующем
запуске сохранённое состояние не обязано содержать свидетельство этого события.
Невозможно одновременно доказать, что незаписанный denial всегда переживёт
такой сбой, и без дополнительных условий обещать показ last-known private data
offline после каждого запуска. Нужен явный дизайн recovery и его последствия
для offline UX; эта заметка не выбирает скрыто дополнительную блокировку.

Кроме того, Swift actor reentrancy и отдельный SQLite writer требуют конкретного
контракта координации: просто назвать компонент actor или serial queue
недостаточно. [Swift Evolution SE-0306](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0306-actors.md)
описывает, как другая actor-isolated работа может выполняться во время suspension.
Реальное исполнение, прерывания и межпроцессный доступ предстоит
проверить на выбранной реализации; формальная запись порядка сама по себе не
даёт такой гарантии.
