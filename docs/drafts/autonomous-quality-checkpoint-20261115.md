# GitView: качество автономного графа на 15 ноября

## Дополнение: срез после `4f7d81f`

Авторская повторная оценка по текущим файлам, не независимое review и не
implementation readiness. Изменения после исходного checkpoint добавили
предложения для связи Issue/PR, Project edit, первой истории метрик,
подключения и частичного доступа; также исправлена default ontology selection
в project config на выбранную draft.11. Каждое из этих уточнений имеет свой
статус и доказательства; они не означают принятия всего графа.

При прямом чтении 124 `GITVIEW-SPEC-*.yaml` все имеют `idea / pre_canonical`.
Всего в них 13 034 строки; в явном поле `specification.scenarios` — 1 219
записей, включая 98 в 500-строчном [0043](GITVIEW-SPEC-0043.yaml). Подсчёт
не включает сценарии в других полях и не определяет число уникальных случаев,
их качество или исполнение. Это сигнал риска для сопровождения: повторённые
правила сложнее сверять с родителями и обновлять без расхождения. Следует
проверить смысловые дубликаты и разбить приёмку по пользовательским маршрутам,
сохраняя уникальные условия и ссылки; не удалять случаи только из-за числа.

Что качество уже позволяет утверждать: для верхнего пользовательского пути
зафиксированы Project membership, Today с сохранением завершённых объектов,
независимые статусы, preview, источник, partial data и выбранные метрики.
Существуют явные сценарии ошибок и границы evidence. Проверка формы, ссылок
и vocabulary помогает находить технические расхождения — например, здесь
обнаружилась устаревшая default ontology selection. Это полезный результат
автономной работы, но текст и его review созданы одним агентом.

Что пока не доказано: семантическая полнота всех ветвей, независимая проверка
соответствия исходной беседе, непротиворечивость всех сценариев и готовность
конкретных листьев к самостоятельной реализации. Не выбраны окончательные
source-to-field операции и права для всего объёма, физический storage/provider
и его миграция, публичные интерфейсы и подтверждённая native механика.
Существующая чистая модель Today и структурные проверки не заменяют этих
решений, а отсутствие будущего device test само по себе не является дефектом
черновой спецификации.

Следующий приоритет — **содержательная консолидация графа**, а не дальнейшее
добавление похожих сценариев: сначала для 0043 составить карту уникальных
пользовательских маршрутов и проверяемых инвариантов с привязкой к исходным
решениям и подчинённым узлам; затем сохранить существенные отрицательные
случаи и выявить точные повторы. Изменение структуры выполнять с проверкой
ссылок и сохранением истории, не выдавая сокращение за улучшение покрытия.
Параллельно на выбранном маршруте отдельно решить оставшиеся входы/выходы
реализационного листа и указать, какие результаты ещё требуют source,
storage или native evidence.

Это авторский checkpoint на содержимом `33255f6`, а не независимое review,
canonical acceptance или разрешение начинать реализацию. Он оценивает, что
уже определено в проектных кандидатах и что ещё мешает использовать их как
полное задание разработчику. Не каждое отсутствие будущего device test
является пробелом самой спецификации; невыбранное поведение или интерфейс,
без которого нельзя построить компонент, им остаётся.

## Существенные оставшиеся решения

1. **Состав и представление данных GitHub.** Для каждого выбранного поля и
   основной выборки нужно выбрать и обосновать фактическую операцию, разрешения,
   identity association и трактовку неполного результата. При невозможности
   доказать полноту маршрут должен оставаться полезным как ограниченное
   наблюдение. Конкретные размеры страниц и численные API budgets не являются
   предварительным условием этой смысловой работы. См. [0100](GITVIEW-SPEC-0100.yaml),
   [0101](GITVIEW-SPEC-0101.yaml), [0102](GITVIEW-SPEC-0102.yaml).
2. **Локальная реализация гарантий.** Предложение SQLite ещё не задаёт полную
   физическую схему, provider, миграцию и конкретный порядок координации
   записи, доступа и очистки. Логические требования нельзя считать готовым
   исполнимым контрактом только из-за выбора технологии. См.
   [0113](GITVIEW-SPEC-0113.yaml), [0117](GITVIEW-SPEC-0117.yaml),
   [0122](GITVIEW-SPEC-0122.yaml), [0123](GITVIEW-SPEC-0123.yaml).
3. **Публичные границы сборки.** Требуется свести Project, observation,
   source, clock, access и navigation к согласованным входам и выходам
   модулей, проверить применимость выбранной версии SpecificationCore и FSD.
   См. [0107](GITVIEW-SPEC-0107.yaml), [0110](GITVIEW-SPEC-0110.yaml),
   [0115](GITVIEW-SPEC-0115.yaml), [0119](GITVIEW-SPEC-0119.yaml).
4. **Нативные взаимодействия.** Нужно выбрать достаточно конкретные
   контракты масштабирования, preview, открытий и доступных альтернатив,
   сохранив возможность последующей проверки на устройстве. Нет оснований
   считать, что формальное описание уже установило совместимость жестов или
   реальное поведение VoiceOver. См. [0075](GITVIEW-SPEC-0075.yaml),
   [0093](GITVIEW-SPEC-0093.yaml), [0120](GITVIEW-SPEC-0120.yaml),
   [0121](GITVIEW-SPEC-0121.yaml).
5. **Авторский процесс.** Обязательные разделы Issue и PR согласованы, но
   participating repositories, пути создания, checkpoint и полномочия ещё
   не выбраны. Это внешняя процессная ветвь, а не полномочие GitView изменять
   GitHub. См. [0090](GITVIEW-SPEC-0090.yaml).

Дополнительно собственный источник GitHub participating-Users в
[0077](GITVIEW-SPEC-0077.yaml) является предложенным, явно ограниченным
счётчиком: его полнота для агентов и других акторов не установлена. Fixed
PR cohort [0055](GITVIEW-SPEC-0055.yaml) остаётся отдельным предложением с
невыбранным release scope; динамический Today не требует его захвата.

## Как оценивать следующий прогон

- Начинать с пользовательского маршрута и его родительских обязательств,
  затем проверять применимые уточнения и транзитивные зависимости. Обратная
  ссылка в тексте не обязательно является prerequisite; формальное замыкание
  родителя может не включать downstream refinements.
- Для каждого листа текущего объёма проверить определённость результата,
  входов и выходов, контекста, ошибок, сценариев и способа проверки в
  контексте родителей. Отдельно записать необязательные возможности и
  отложенные подтверждения platform/source; не считать их по умолчанию
  реализованным поведением.
- `next-move --candidate-file` в применявшемся runtime проверял YAML mapping,
  kind и соответствие ID; `checked` не означает semantic review. Проверка
  composition ограничена её выбранным контекстом и vocabulary; структурная
  проверка рёбер не доказывает достаточно полных требований.
- Фактические Swift tests, авторизованный GitHub, persistent restart и native
  device observations после реализации дают разные виды evidence. Ни один из
  них не заменяется этим checkpoint или будущим mock-only тестом.

Следующий приоритет — проследить один целый маршрут от выбранных операций
GitHub и границы хранения до доступного списка и его состояний, закрывая
входы и выходы по существу, а не добавляя новые узлы ради количества.
