# GitView: текущий срез готовности графа

Дополнение: после указанного ниже снимка рабочая композиция обновлена до
draft.11. [Сравнение и ограничения](../../ontology/candidates/domain-v0.2.0-draft.11/README.md)
сохранены отдельно; остальные выводы остаются оценкой указанного commit.

Авторский обзор состояния на commit `96e2b4a`, без semantic approval и без
реализации приложения. Исходные требования — [root intent](../../.specgraph/root_intent.md),
[0001](GITVIEW-SPEC-0001.yaml), согласованные составы PR/Issue, история беседы
и сохранённые прототипы. Дальнейшие точные правила явно остаются кандидатами
агента. Это не исчерпывающий независимый review каждого листа и не разрешение
начинать реализацию до готовности общего графа и его зависимостей.

Текущий инвентарь: 123 candidate YAML, все `idea / pre_canonical`, 55 листьев
по `refines`, отсутствующих целей и циклов по проверенным объявленным рёбрам
нет, все узлы достижимы от 0001 через `refines`. Проверка формы и словаря
не доказывает ни полноту смысловых зависимостей, ни правильность сценариев.
Смысловая ссылка в тексте не всегда означает объявленное `depends_on`; нельзя
добавлять её автоматически, поскольку направление ответственности может быть
другим и прямое ребро может образовать цикл. Для каждого implementation leaf
нужны отдельная проверка контракта и замыкания реальных предпосылок.

Часть узлов представляет сквозные правила или deferred scope, поэтому не все

## Важные пробелы на уровне всего графа

1. **Ontology.** Рабочая композиция `domain-v0.2.0-draft.10` — draft;
   её [README](../../ontology/candidates/domain-v0.2.0-draft.10/README.md)
   отмечает warning/gap 0001 и неподтверждённое происхождение compiler.
   Совпадение vocabulary не утверждает смысл терминов и relationships.
   Нужна сверка всех используемых предметных понятий и действий с выбранной
   композицией, без превращения UI controls в ontology entities.
2. **Source coverage.** [0100](GITVIEW-SPEC-0100.yaml) и
   [0102](GITVIEW-SPEC-0102.yaml) формулируют границы, но сами признают,
   что соответствие всех выбранных полей, разрешений и покрытий не доказано.
   Особенно важно различать полный count и материализованный список, текущие
   данные и историю, а также недоступность и ноль. Численные API budgets пока
   не являются решением этой проблемы и не выбираются здесь.
3. **Устройства и provider.** Текстовые сценарии не устанавливают работу iOS
   gesture arbitration, accessibility, system sharing, SQLite/Keychain или
   фактическую GitHub authorization. До implementation readiness необходимо
   определить проверяемые границы и предпосылки; сами наблюдения продукта
   возможны только после авторизованной реализации.
4. **Качество автономной спецификации.** История показывает полезные находки
   противоречий, но у этой работы тот же автор, что и у проверяемых правил.
   Нужны проверка против первичных требований, отрицательные примеры,
   трассировка по всем ветвям и независимое содержательное review. Нельзя
   выводить процент готовности из количества nodes или `checked`.

## Следующий проход

Начать с онтологии и 0001: повторно определить содержание прежнего warning/gap в
рабочей композиции, затем сверить выбранные PR/Issue, Project и действия с
formal package. После этого вести по каждой ветви отдельную таблицу: требование,
родитель, implementation leaf, зависимости, нерешённые контракты и нужное
evidence. При обнаружении противоречия менять соответствующий источник и
проверять затронутых родителей и потребителей, не объявляя весь граф готовым.
