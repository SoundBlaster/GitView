# Формат описаний Issue и PR

Статус: черновик формата. Пользователь предложил обязательные шаблоны с
разделами «Мотивация», «Проблема» и другими (`conversation:gitview/excerpt-37`).
Обязательность — требование пользователя к процессу; конкретные заголовки,
дополнительные разделы, область внедрения и проверки ниже предложены агентом
и ещё не согласованы. Файлы здесь не установлены как активные GitHub templates.

Заготовки: [Issue](issue.md) и [PR](pull-request.md).

## Общее ядро — предложение

| Раздел | Вопрос |
| --- | --- |
| `Problem` | Какова исходная проблема или неудовлетворённая потребность? |
| `Motivation` | Почему за неё берёмся: чья цель и какая ожидаемая польза? |
| `Expected outcome` | Какое наблюдаемое изменение хотим получить? |

Для PR добавлены `Changes` — что предложено изменить, и `Validation` —
что реально проверено и с каким результатом. `References` хранит ссылки на
исходные требования, Issue и контекст; наличие отдельной Issue не обязательно
для каждого PR. В PR основное содержание должно читаться без перехода по ссылке.

Motivation — явное заявление автора описания. Сохраняем текст и его источник;
оно позволяет обсуждать мотив без догадки из голой ссылки Issue → PR.
Автор описания при этом не обязательно актор каждого изменения кода.
Ссылки, заявление мотива, предложенное последствие и подтверждённый результат
различаются. Незаполненный раздел не даёт агенту права выдумать мотив.

`Expected outcome` описывает намерение и в Issue, и в PR; ни создание PR,
ни заполнение раздела не подтверждает достижение результата. Это устанавливают
данные о проверках и отдельные решения о принятии.

## Обязательность и внедрение

Предлагаемый способ: согласованный формат + инструкции агентам при создании
и обновлении описаний + автоматическая проверка заполненности. Проверка структуры
не подтверждает истинность написанного. Для создания через CLI/API инструкции и
проверка нужны отдельно от подсказок веб-формы. Конкретные gates ещё не выбраны
и не реализованы.

GitHub поддерживает обязательные поля в Issue Forms; PR template подставляет
текст в описание, а Issue Forms для PR не поддерживаются. Поэтому наличие
одного файла шаблона не устанавливает одинаковый механизм обязательности для
Issue и PR. См. [GitHub Issue Forms](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)
и [GitHub form schema](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-githubs-form-schema).

Сначала согласуем формат; затем определим репозитории внедрения и механизм
проверки. Работа с репозиториями без нашего шаблона и чтение старых описаний
остаются отдельным вопросом. Требование к созданию описаний не означает,
что GitView отказывается отображать объекты другого формата.

Точные правила извлечения разделов в GitView, версии формата, обработка
изменений текста и различение заявленных мотивов от выводов агента относятся
к будущим спецификациям. Этот черновик не добавляет классы в ontology package.

Источник пользователя — локальный фрагмент беседы, не удостоверенный ID
сообщения. Дословная цитата хранится в SpecDraft отдельно от этого предложения.
