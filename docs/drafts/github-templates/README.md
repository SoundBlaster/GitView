# Формат описаний Issue и PR

## Рабочий процесс для GitView

В [0090](../GITVIEW-SPEC-0090.yaml) выбран начальный процесс для GitView: агент проверяет фактическое описание перед созданием или изменением, а веб-формы и шаблон помогают человеку заполнить разделы. Форма и шаблон не доказывают покрытие всех способов создания; внешние пути и реальная установка ещё не проверены. GitView остаётся локальным репозиторием, и сами файлы здесь не являются включёнными GitHub templates.

## Уточнение чтения и проверки

[0051](../GITVIEW-SPEC-0051.yaml) и [0076](../GITVIEW-SPEC-0076.yaml)
теперь согласованы для узкого рабочего случая: раздел, содержащий только
комментарий шаблона и буквальное `TODO` или `TBD` без учёта регистра ASCII,
считается незаполненным. Более длинная фраза не считается таким placeholder
автоматически и не подтверждает истинность или полезность текста. При этом
GitView сохраняет исходное описание и не утверждает, что внешний процесс
проверки запускался. Профиль и оценка привязаны к конкретной версии тела;
старый результат нельзя молча выдать за проверку по изменённому правилу.

Начальный scope GitView и агентский pre-submit checkpoint выбраны в 0090; реальные пути GitHub, их настройка и фактическое покрытие пока не установлены. Это не активные шаблоны, не работающий
checker и не изменение исходных Issue или PR. [Примеры](../evidence/description-recognition-examples.yaml)
являются fixtures для review, а не результатами исполнения parser.

Статус: формат описаний согласован пользователем (`conversation:gitview/excerpt-38`:
«Меня устраивают и поля issue и форматы описаний»). Обязательность шаблонов —
ранее сформулированное требование к процессу (`excerpt-37`). Согласованы разделы
Issue и PR ниже. Начальная область и агентский checkpoint выбраны в 0090; настройка и проверка реальных путей не выполнены;
файлы здесь не установлены как активные GitHub templates. Это не утверждение
всего sketch или ontology package.

Заготовки: [Issue](issue.md) и [PR](pull-request.md).

## Согласованное общее ядро

| Раздел | Вопрос |
| --- | --- |
| `Problem` | Какова исходная проблема или неудовлетворённая потребность? |
| `Motivation` | Почему за неё берёмся: чья цель и какая ожидаемая польза? |
| `Expected outcome` | Какое наблюдаемое изменение хотим получить? |
| `References` | На какие исходные требования, Issue или контекст опирается описание? |

Для PR добавлены `Changes` — что предложено изменить, и `Validation` —
что реально проверено и с каким результатом. `References` хранит ссылки на
исходные требования, Issue и контекст; наличие отдельной Issue не обязательно
для каждого PR. В PR основное содержание должно читаться без перехода по ссылке.

Motivation — явное заявление автора описания. Сохраняем текст и его источник;
оно позволяет обсуждать мотив без догадки из голой ссылки Issue → PR.
Автор описания при этом не обязательно актор каждого изменения кода.
Ссылки, заявление мотива, предложенное последствие и подтверждённый результат
различаются. Незаполненный раздел не даёт агенту права выдумать мотив.

`Expected outcome` описывает намерение и в Issue, и в PR; ни создание PR,
ни заполнение раздела не подтверждает достижение результата. Это устанавливают
данные о проверках и отдельные решения о принятии.

## Обязательность и внедрение

Предлагаемый способ: согласованный формат + инструкции агентам при создании
и обновлении описаний + автоматическая проверка заполненности. Проверка структуры
не подтверждает истинность написанного. Для создания через CLI/API инструкции и
проверка нужны отдельно от подсказок веб-формы. Конкретные gates ещё не выбраны
и не реализованы.

GitHub поддерживает обязательные поля в Issue Forms; PR template подставляет
текст в описание, а Issue Forms для PR не поддерживаются. Поэтому наличие
одного файла шаблона не устанавливает одинаковый механизм обязательности для
Issue и PR. См. [GitHub Issue Forms](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)
и [GitHub form schema](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-githubs-form-schema).

Формат согласован владельцем; начальный процесс и его checkpoint — рабочее предложение агента. Привязка к будущему remote и фактическое обеспечение ещё предстоят. Работа с репозиториями без нашего шаблона и чтение старых описаний
остаются отдельным вопросом. Требование к созданию описаний не означает,
что GitView отказывается отображать объекты другого формата.

Первичный профиль извлечения, версия интерпретации и обработка изменений текста
описаны как кандидаты в 0051 и 0076; расширение синтаксиса и реальная проверка
остаётся дальнейшей работой. Заявленный мотив отличается от выводов агента.
Этот черновик не добавляет классы в ontology package.

Источник пользователя — локальный фрагмент беседы, не удостоверенный ID
сообщения. Дословная цитата хранится в SpecDraft отдельно от этого предложения.
