# GitView: предложение уровней масштаба

Статус: предложение агента по запросу «Ок. Сочиняй»
(`conversation:gitview/excerpt-42`). Основа — согласованные свойства Project,
PR и Issue, два пути погружения и Apple Look. Уровни, плотность, жесты и
состав видимых деталей ниже требуют выбора; это не canonical UX specification
и не реализация приложения.

## Основная идея

Приближаем выбранную часть работы: Projects → репозитории выбранного Project →
PR/Issue выбранного репозитория → обзор одного PR/Issue. Приближение внутри
области постепенно раскрывает сведения; переход в другую область явно меняет
заголовок и контекст. Вложенность экрана не вводит новые ontology entities.

У масштаба два эффекта: плотность сетки и область обзора. Их различие должно
быть понятно пользователю. На одном масштабе видны несколько маленьких карточек,
на другом — меньше карточек с большим количеством сведений. Переход внутрь
объекта происходит вокруг устойчивого фокуса под пальцами; не выбираем случайный
объект между двумя карточками. Точные пороги и конфликт с прокруткой проверим
прототипом. Tap даёт явное раскрытие, Back — возврат; pinch не единственный путь.

## 0. Общая сетка Projects

Вопрос: «Какие проекты требуют моего внимания?»

- Компактная квадратная карточка: имя Project, число репозиториев.
- По мере увеличения: открытые PR / Issue и число PR с красным CI.
- При достаточном месте: ожидание review и краткая сводка результатов за период.
- Неполнота и актуальность видны без погружения. Цвет относится к конкретному
  сигналу; вся карточка не получает единую оценку «здоровья».

Несколько ступеней плотности относятся к тем же Projects. На самой плотной
сетке не пытаемся уместить полный dashboard: сохраняем узнаваемые имена и
минимум сигналов. Итог портфеля считает уникальные репозитории, даже когда
они входят в несколько Projects.

## 1. Внутри Project — сетка репозиториев

Вопрос: «В какой части проекта происходит работа?»

Заголовок содержит имя Project. Сводка над сеткой относится ко всем его
репозиториям; период результатов и применённые фильтры видны явно.
Карточки репозиториев постепенно раскрывают:

1. Имя с owner, открытые PR / Issue.
2. Draft, review, красный CI, незакрытые треды и актуальность.
3. При дальнейшем раскрытии — результаты за период и график, когда есть история.

Количество объектов и число затронутых репозиториев различаются, например
«3 PR с красным CI в 2 репозиториях». Репозитории разных organizations
остаются в одной сетке проекта.

Для Project с одним репозиторием этот промежуточный экран пропускаем:
раскрываются его PR/Issue. Название Project и репозиторий остаются различимыми
в контексте; возврат ведёт к той же карточке Project.

## 2. PR и Issue в выбранной области

Вопрос: «Какие конкретно объекты посмотреть?»

Обычно область — Repository. Прямой переход из счётчика Project открывает
общую выборку его репозиториев: это тот же уровень деталей объектов с другой
областью, не обязательный обход Repository и не новый тип сущности.

Сетка содержит различимые PR и Issue; доступны выбор типа и явные фильтры.
Плотность определяет состав карточки:

| Вид | Компактно | При приближении |
| --- | --- | --- |
| PR | Тип/номер, короткое название, lifecycle и отдельный draft | Итог review, CI по цветам и всего, счётчики тредов, строк, файлов и коммитов |
| Issue | Тип/номер, короткое название, состояние | Причина состояния, labels/type, assignees, комментарии, участники, sub-issues и blockers |

В общей выборке Project у каждой карточки виден исходный репозиторий, чтобы
одинаковые номера объектов не путались. Числа не зависят от того, сколько
карточек загружено в видимой части сетки. Загрузка и неполнота обозначаются.

Если нужные сведения не помещаются при крупном системном шрифте, предлагаем
более свободную раскладку, включая системный список; не уменьшаем текст ради
заданного числа колонок. Число колонок — адаптивное, не продуктовая константа.

## 3. Обзор одного PR / Issue

Вопрос: «Что это, зачем появилось и что с ним сейчас?»

Крупная карточка раскрывается в экран обзора. Общая последовательность:

1. Репозиторий, тип/номер, полное название и исходное состояние.
2. Компактные метрики: PR — review, CI, треды и размер изменений;
   Issue — обсуждение, sub-issues и явные блокировки.
3. `Problem`, `Motivation`, `Expected outcome`; PR также `Changes` и `Validation`.
4. `References`, автор, участники/назначения, labels и даты — по мере раскрытия.
5. Перейти на GitHub и системный sharing.

Все согласованные поля доступны в обзоре, но не обязаны быть видны одновременно.
Большой текст разделов можно раскрыть. Разделы без данных не заполняются
сгенерированными объяснениями. `Validation` — заявление автора; CI — отдельные
наблюдаемые данные. Признак свежести сохраняется.

Обзор не добавляет внутренний просмотр diff, содержимого ReviewThread,
логов прогонов, редактор комментариев, approve или merge. Счётчики не обещают
несогласованного уровня погружения; подробности доступны через первоисточник.
Область sharing для private данных ещё требует отдельной спецификации.

## Путь через сигнал

Пример: Projects → Project «Apple Apps» → счётчик «3 PR с красным CI» →
эти три PR с указанием репозитория → обзор выбранного PR → GitHub.

В заголовке выборки одновременно видны Project и условие «красный CI».
При изменении плотности условие сохраняется; Back возвращает в исходный
Project с прежним масштабом и позицией. Если состояние PR обновилось и он
перестал соответствовать фильтру, открытый обзор не исчезает. В нём отражается
новое состояние; изменение состава сетки выполняется предсказуемо при возврате.
Порядок карточек не пересортировывается посреди жеста или чтения.

## Календарь — отдельный эксперимент времени

Календарная клетка — день, а клетка основной сетки — Project, Repository или
объект. Поэтому календарь предлагаем как отдельное представление в общей
области обзора, с явным переключением «Проекты / Время». Он может ощущаться
самым дальним обзором, но не является автоматической заменой клеток Projects
на дни при каждом уменьшении.

Выбор дня показывает подтверждённые события за этот день в выбранной области,
когда есть нужная история. Он не означает восстановление состояния всех PR
на тот момент. Текущие CI/review не окрашивают прошлые дни как исторический факт.
Состав событий, шкала интенсивности и отношение к гипотезе Activity пока открыты.
Этот режим не обязателен для первого UX-среза.

## Переходы и Apple Look

- В каждом переходе сохраняем идентичность фокуса, область, фильтр, позицию
  и предыдущую плотность для возврата. Один Repository в двух Projects открывается
  в контексте того Project, из которого пришли.
- Период влияет на результаты/графики; дата сама по себе не превращает текущие
  счётчики в исторические. Область, тип объектов и период не меняются скрыто.
- Используем системные цвета, типографику, SF Symbols, навигацию, меню и sharing.
  Liquid Glass относится к навигационным элементам и контролам; основная
  информация остаётся читаемой на спокойной поверхности.
- Pinch сопровождается доступными способами раскрыть объект, изменить плотность
  и вернуться. Важные сигналы имеют текст/символы, а не только цвет.
- Движение адаптируется к Reduce Motion; фокус VoiceOver и крупный шрифт
  учитываются в сценарии возврата. Конкретные API и deployment target пока
  не выбираем; наличие готового системного Photos-подобного компонента не заявлено.

## Предложение для первого прототипа

Показать общий обзор Projects, раскрытие одного многорепозиторного Project,
его сетку объектов, обзор PR и Issue, прямой переход через CI-счётчик и возврат.
Добавить пример Project из одного репозитория, неполные данные и крупный шрифт.
Календарь оставить отдельным экспериментом. Прототип должен проверить, понятно
ли меняется область и удаётся ли вернуться без потери места; код приложения
этим предложением не запрашивается.
