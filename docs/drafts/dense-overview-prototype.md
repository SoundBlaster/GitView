# Плотный обзор и «телескоп» без смены области

Статус: пользователь уточнил основную идею масштабирования (`excerpt-46`),
затем подтвердил показанную концепцию: «Очень круто. То что нужно!»
(`conversation:gitview/excerpt-47`). Подтверждены многие плотности в одной
области и скользящий preview с сохранением общего обзора. Это не утверждение
всех числовых параметров жеста, цветов, ontology package или всего sketch.
Предыдущий макет показывал сразу крупную
плотность — две карточки в ряд. Он не представлял весь диапазон масштаба.
Один и тот же набор PR/Issue должен иметь множество плотностей; preview особенно
важен для мелких клеток. Конкретные размеры и кодировка клеток уточняются далее.

## Смысл уточнения

- Область Project / Repository и плотность её сетки — разные измерения.
- Сценарий масштаба: около 100 PR за день в репозитории; на экране порядка
  100 маленьких клеток, например 8 колонок и 12–13 рядов.
- При приближении клетки увеличиваются и раскрывают информацию в пределах
  той же области. Обзор с двумя карточками в ряд — лишь крупный край диапазона.
- На мелком масштабе пользователь рассматривает объекты через один rich preview,
  перемещаясь пальцем между клетками и сохраняя общий обзор — аналог «телескопа».
- Цвета и значки требуют отдельных правил смысла. CI, исходное состояние PR/Issue
  и готовность к merge не становятся одной шкалой.
- Неуверенное упоминание других объектов не вводит новые entity types или
  обязательный отдельный экран проверок.

Дата/«100 в день» здесь описывает нагрузку и пример масштаба; конкретный
фильтр по дате и история событий ещё требуют спецификации.

## Интерактивный пример

По последующему запросу пользователя (`excerpt-48`) сохранена независимая
[HTML/CSS/JS-версия](../../prototypes/dense-overview/index.html) с локальными
ресурсами. [Каталог и запуск](../../prototypes/README.md). Исходный пример в
беседе сохранён отдельно; дальнейшие правки не синхронизируются автоматически.

Исходник для показа прямо в беседе:
`/Users/egor/.codex/visualizations/2026/10/26/01a179ec-2ed5-7923-bdb1-b24739653482/gitview-dense-overview.html`.

Предложения агента, показанные в примере:

- 100 вымышленных объектов: 80 PR и 20 Issue, без запросов к GitHub.
- Исходно 8 колонок; диапазон 2–10. Ползунок позволяет проверить масштаб мышью;
  два touch-контакта меняют число колонок по расстоянию между ними.
- Набор и область остаются теми же; на мелком масштабе видны тип и номер,
  при приближении — заголовок и дополнительные сведения.
- Цвет PR иллюстрирует CI: красный, жёлтый, зелёный; неполные данные и Issue
  нейтральны, тип различается значком. Эта конкретная кодировка ещё не выбрана.
- Desktop hover показывает один бабл. На touch: long press около 480 ms →
  движение между клетками → обновление того же бабла; отпускание закрывает его.
  Жест не открывает объект автоматически. Сетка не размывается и не затемняется.
- Бабл появляется рядом с точкой взаимодействия, с учётом краёв экрана.
  В нём название, номер/тип, состояние, метрики и короткая Motivation.
- Обычное вертикальное движение до удержания и колесо прокручивают набор
  при крупном масштабе. Tap открывает объект; возврат сохраняет плотность и место.
- Граница видимой области фиксирована в пределах макета телефона; виртуальное
  положение ячеек меняется без огромного роста высоты всей визуализации.
- Масштабирование использует ступени колонок и анимацию перестройки.
  Это не доказательство непрерывности нативной Collection View на устройстве.

Макет относится к одному Project с одним Repository, поэтому сокращённый путь
ведёт прямо к объектам; сетка нескольких репозиториев здесь не показана.
Этот пример развивает будущий скользящий режим, не переносит его автоматически
в обязательный объём первой версии. Он не реализует iOS-приложение.

## Проверки и пределы

В браузере проверены 100 клеток, hover, удержание мышью и скольжение, смена
плотности, прокрутка, открытие объекта и возврат с совпадением положения и
масштаба. При ширине 320 px не обнаружено горизонтального overflow; бабл в
пределах изображённого экрана. Просмотрен тёмный плотный обзор.

С включённой touch-эмуляцией Chromium проверены long press → touch move на
соседнюю клетку (preview сменился на PR #103), отпускание и pinch 8 → 4 колонки.
Первоначальные попытки без включённой эмуляции не считаются проверкой жеста.
Нативный UIKit/SwiftUI, физический iPhone, полная доступность и производительность
на больших реальных наборах этим не проверены.

Следующий вопрос: какие признаки кодировать в клетке каждого типа на самом
плотном масштабе. Следующая проверка взаимодействия — устойчивость выбранной
клетки и возврата при приближении вокруг неё на реальном устройстве.

Исходная речь сохранена дословно в SpecDraft отдельно от предложения агента.
Проверка макета не утверждает ontology package или весь sketch.
