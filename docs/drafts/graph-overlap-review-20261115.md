## Пять прямых зависимостей 0043

Для каждого ребра отчёт находит другой путь по `depends_on`. Указаны конкретные
сценарии [0043](GITVIEW-SPEC-0043.yaml), которые связывают это обязательство с
другими ветвями. Это ручной разбор примеров, не доказательство минимального
набора рёбер или машинной семантики условных зависимостей.

| Ребро и один обходной путь | Сквозное обязательство | Оценка |
| --- | --- | --- |
| 0043 → [0022](GITVIEW-SPEC-0022.yaml); через 0059 | `first_overview`: после подтверждённого setup два Project из разных организаций доступны как разные Projects. | Прямая связь объясняет зависимость начального пользовательского пути от setup; 0059 касается discovery и не заменяет по смыслу всю начальную сборку. Сохранить до определения проверяемого контракта транзитивности. |
| 0043 → [0023](GITVIEW-SPEC-0023.yaml); через 0024 | `portfolio_return_with_partial_local_read`: ограничение чтения Q видно после возврата, P не подставляется вместо Q. | 0023 задаёт смысл неполного состояния обзора, 0024 — контекст возврата. Оба необходимы сценарию; сохранение прямой связи делает основание состояния явным. |
| 0043 → [0024](GITVIEW-SPEC-0024.yaml); через 0031 | `preview_and_source`: PR из нужного Repository сохраняет identity и контекст при preview, переходе к источнику и возврате. | 0031 уточняет preview, 0024 — более широкий контекст навигации и возврата. Оставить прямую связь для сквозного требования, а не выводить её из существования альтернативного пути. |
| 0043 → [0025](GITVIEW-SPEC-0025.yaml); через 0022 | `shared_repository`: один Repository в двух Projects учитывается в каждом, но один раз в уникальном итоге; источник не меняется. | Membership и lifecycle Project имеют смысл и после setup; прохождение через 0022 не заменяет эту самостоятельную границу. |
| 0043 → [0027](GITVIEW-SPEC-0027.yaml); через 0029 | `work_completes`: 95 влитых сегодня PR остаются в Today, пока пользователь явно не исключит их. | 0027 задаёт выборку Today, а 0029 — контекст сводки и уникальности. Наличие обхода не обосновывает отказ от явной связи с правилом выборки. |

Решение для этой выборки — сохранить рёбра. Это не означает, что остальные 47
рёбер 0043 с обходом необходимы. В установленном runtime status readiness и
trace проверяют непосредственные зависимости; удаление ребра может изменить
проверку даже при существовании другого пути. Его эффект надо оценивать для
конкретного механизма, а не предполагать транзитивный gate.

## 0104 и 0105: похожая формулировка

На снимке сравнивались `0104#acceptance[5]` и `0105#acceptance[4]`, где индекс
начинается с нуля. Классификация: **общая норма с разными обязанностями**, не
две одинаковые операции и не конфликт.

[0040](GITVIEW-SPEC-0040.yaml) задаёт инъекцию сетевых и data dependencies и
отделяет детерминированные проверки от real integration evidence;
[0095](GITVIEW-SPEC-0095.yaml) уточняет заменяемость эффектов на границах.
При этом [0104](GITVIEW-SPEC-0104.yaml) отвечает за чтение, редактирование и
восстановление конфигурации Project, а [0105](GITVIEW-SPEC-0105.yaml) — за
сохранение наблюдений, контекстов и покрытия. У обоих есть собственные
сценарии сбоев и доказательств; успешная проверка одного не проверяет другой.

Формулировки этих двух acceptance уточнены по их области. Общая норма уже
выражена в 0040/0095, а локальные условия оставлены для проверки каждой
границы. Это читаемая смысловая связь, не утверждение о поддержке SpecGraph
машинного наследования требований. `0104` остаётся составным кандидатом с
default-association; `0105` не выбирает конкретное хранилище.
