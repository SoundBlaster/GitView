# Project по умолчанию: граница решения и стоимость уточнений

## Что согласовано

[Project proposal](project-summary-proposal.md) фиксирует один Project на один
Repository по умолчанию, допускает несколько Repository в Project и один
Repository в разных Projects. В [корневом черновике](GITVIEW-SPEC-0001.yaml)
механика создания, именования и синхронизации такого Project остаётся открытой.
Из этих решений не следует однозначно постоянная маркировка одного Project как
«default» или повторный экран подтверждения при каждом повторном setup.

## Рабочий вариант агента

[0025](GITVIEW-SPEC-0025.yaml), [0045](GITVIEW-SPEC-0045.yaml) и
[0052](GITVIEW-SPEC-0052.yaml) предлагают сохранять default association от
Repository к Project. Setup повторно использует эту association; изменённый
Project может сохранить её, пока содержит Repository; удаление участника или
Project прекращает association. Для повторов, частичного batch и прерванной
записи предложены отдельные правила. Это целостный рабочий вариант для
спецификации, но не отдельно выбранный владельцем механизм и не факт наличия
реализации. Пользователь разрешил автономное уточнение; его решение о составе
Project не следует переименовывать в подтверждение этих частных правил.

У варианта есть полезное свойство: повторное setup может предсказуемо
обнаружить тот же специальный Project даже после его переименования и
расширения. Оно имеет цену: нужны правила идентичности, удаления association,
конкурирующих операций и восстановления. В частности, дополнительный Project
с тем же Repository сам по себе не считается default, даже когда содержит
единственный Repository. Это выбор семантики, а не следствие отношения членства.

Другой возможный дизайн — предлагать однорепозиторный Project при явном
добавлении, разрешая обычное редактирование и отдельно определяя поведение
повторного добавления без постоянной привилегированной association. Для него
нужны проверяемые правила разрешения неоднозначности между несколькими Projects,
повторов и незавершённой записи; нельзя считать такой вариант автоматически
эквивалентным или более простым, пока эти правила не заданы.

## Сравнение на одинаковых пользовательских сценариях

| Сценарий | Постоянная association | Только предложение при создании |
| --- | --- | --- |
| Впервые выбран R | Предлагается один новый Project для R. | Предлагается один новый Project для R. |
| R выбран повторно без изменений | Повторно используется назначенный Project. | Нужна политика поиска и явного выбора существующего Project или создания нового. |
| Project переименован и дополнен S | Тот же Project остаётся default для R, пока содержит R. | Совпадение состава и имени больше не распознаёт исходный выбор; требуется отдельный выбор либо дополнительный признак. |
| R входит в P и Q | Association однозначно указывает default; Q не меняется. | Одно членство не определяет, какой из P и Q предлагать. |
| R удалён из P | Association к P снимается; P и другие Projects сохраняются. | P сохраняется; новый setup требует обычного решения о выборе или создании. |
| Потерян ответ сохранения | Необходимо согласовать действительную запись и исход операции; повтор не должен создать случайный дубликат. | Та же необходимость сохраняется, хотя точные данные для сопоставления могут отличаться. |

Обе колонки являются описаниями кандидатов, а не замерами сложности,
проверкой iOS или доказательством их эквивалентности. Второй вариант становится
сложнее в момент, когда продукту требуется бесшовно распознать исходный Project
после смены названия и состава; он может быть проще, если явно показывать
пользователю выбор. Такой выбор и его доступность пока не спроектированы.

## Рабочее решение для графа

Оставляю **association как текущий рабочий вариант**: она однозначно связывает
повторный setup с ранее выбранным Project при общем членстве и переживает
переименование и добавление других Repository. Это решение агента в рамках
порученного автономного уточнения, не дополнительное утверждение пользователя
и не доказательство, что иная модель хуже. Оно сохраняет возможность нескольких
Projects с одинаковым составом. Дальнейшее UX-исследование может изменить его;
тогда надо одновременно пересмотреть зависимые сценарии и миграцию данных,
если к тому моменту уже появятся сохранённые данные.

Сам факт выбора association не доказывает необходимость всех предлагаемых
механизмов 0045 и 0108. В частности, сохранение каждого элемента batch и его
отмена через обязательный durable journal — более сильное решение, чем
непосредственная потребность сохранить корректные Projects и не создать
случайные дубликаты. Эту часть нужно сравнить с альтернативой простого
повторного выбора несохранённых Repository после перезапуска, сохраняя честный
статус уже отправленных и потенциально завершившихся операций. Не считать
такую альтернативу автоматически безопасной, пока не определена граница
записи и не проверены конкурентные и прерванные случаи.

## Кандидат упрощения batch setup

Рассматривается отдельный вариант: после прерывания не восстанавливать список
ещё не отправленных выборов и предложить оператору выбрать их заново. Уже
сохранённые Projects читаются из действительного хранилища, а для каждой
потенциально начатой операции сохраняется или восстанавливается достаточно
данных, чтобы не объявить её несостоявшейся и не создать случайный дубликат.
При невозможности установить результат безопасное повторение остаётся
ограниченным. Возобновление неотправленных элементов не происходит само.

| Условие | Предложенный наблюдаемый результат |
| --- | --- |
| Из двух выбранных R1 сохранён, R2 ещё не отправлен, процесс завершился | R1 остаётся в обзоре; повторный выбор R2 может потребоваться. Отсутствие сохранённого выбора R2 не считается подтверждённой неудачей отправленной операции. |
| Сохранение R1 могло начаться, но результат недоступен | Не сообщать ни успех, ни подтверждённую отмену; не запускать конфликтующий повтор до безопасного согласования. |
| Пользователь отменил оставшуюся обработку | Не начинать после отмены новые элементы; уже запущенные эффекты определяются отдельно. После перезапуска не возобновлять старый выбор автоматически. |
| Пользователь осознанно создаёт второй Project с тем же R | Отличать новую явную команду от повтора прежней; не препятствовать ей только из-за совпадения состава. |

Это **альтернатива для последующего сравнения**, а не изменение принятых в
0045 требований и не доказанная crash-safe реализация. До выбора необходимо
определить фактическую границу «отправлен», вариант координации отмены и
новой записи, способы восстановления результата и проверить сценарии с
конкуренцией и рестартом. Если хранение общего подтверждённого намерения
необходимо для этих гарантий, требование остаётся; если нет — в 0045, 0052,
0108, 0113 и связанных сценариях его можно заменить согласованным более
узким контрактом. Приложение и тесты не выполнялись.

## Сохраняемые обязанности

Независимо от выбора механизма, Project и Repository остаются различными,
общие Repository и разные organizations поддерживаются, локальное изменение
не изменяет GitHub и другие Projects, а ошибки и неопределённый результат не
выдаются за подтверждённое сохранение. Повтор операции не должен молча
приводить к непреднамеренному дубликату. Это не запрещает пользователю
осознанно создать разные Projects с одинаковым составом.

## Масштаб влияния и дальнейшая работа

По поиску `default[ -](association|project)` в актуальных YAML на момент этого
обзора найдено 161 строка в 24 файлах: 0001, 0005, 0019, 0022, 0025, 0043,
0045, 0047, 0052, 0072, 0082–0084, 0091, 0099, 0103–0104, 0106–0108, 0111,
0113, 0122 и 0123. Это навигационный текстовый инвентарь: строки могут содержать
примеры, несколько требований или косвенные упоминания; он не измеряет число
самостоятельных обязательств и не доказывает полноту всех синонимов.

Перед возможной заменой рабочего варианта нужно сопоставить cross-branch
зависимости, в том числе назначение 0045, 0052 и 0108, с правилами альтернативы. Нельзя просто удалить association и оставить
сценарии восстановления, multi-Project membership или setup без объяснения.
Альтернативы следует оценить по реализуемым сценариям, размерам действительно
необходимого контракта и наблюдаемому UX; ни один продуктовый код или тест
здесь не исполнялся. Графикам и истории метрик это решение не меняет область.
