# GitView: выборочная сортировка оставшихся черновиков

Снимок после `79dcc8b`. Это авторская сортировка прочитанных примеров по роли в следующем продуктовом проходе, а не отказ от функций и не решение владельца. Название или количество оставшихся draft ID само по себе не означает, что каждому нужен узел в `specs/nodes/`.

| Черновик | Что в нём полезно | Решение для текущего прохода |
| --- | --- | --- |
| [0043](GITVIEW-SPEC-0043.yaml) | Большая подборка сквозных сценариев и границ восстановления. | Не переносить весь перечень и его зависимости автоматически. Ключевые маршруты уже выборочно собраны в [0020](../../specs/nodes/GITVIEW-SPEC-0020.yaml) и [карте маршрутов](product-journey-cross-check-20261116.md); обращаться к остальным примерам при конкретном пробеле. |
| [0052](GITVIEW-SPEC-0052.yaml) | Recovery для одной конкретной модели persistent default association. | Сохранить условным кандидатом. Пользователь выбрал default «один Project на Repository», но не выбрал этот механизм; общая неопределённость сохранения уже отражена в [0045](../../specs/nodes/GITVIEW-SPEC-0045.yaml). |
| [0055](GITVIEW-SPEC-0055.yaml) | Fixed cohort как один из способов смотреть completion/burn-down. | Не объявлять обязательной первой версией или определением Today. Семантика и полезность отдельного cohort ещё не выбраны. |
| [0060](GITVIEW-SPEC-0060.yaml) | Кандидатное сопоставление GitHub check entries, retries и revisions. | Сохранить для source-specific уточнения. Продуктовое различие счётчиков, неизвестности и ревизий уже описано в [0028](../../specs/nodes/GITVIEW-SPEC-0028.yaml); конкретная mapping не подтверждена живой интеграцией. |
| [0069](GITVIEW-SPEC-0069.yaml) | Возможные начальные series, календарные buckets и периоды. | Сохранить как UX-кандидат. Само наличие графиков и правило текущего состава Project уже отражены в [0030](../../specs/nodes/GITVIEW-SPEC-0030.yaml) и [0064](../../specs/nodes/GITVIEW-SPEC-0064.yaml); пресеты и daily buckets не утверждать по умолчанию. |
| [0079](GITVIEW-SPEC-0079.yaml) | Применимость testability, TDD и accessibility на разных уровнях evidence. | Сохранить как кандидат workflow. Выбранные инженерные качества уже видимы в [0021](../../specs/nodes/GITVIEW-SPEC-0021.yaml) и [0040](../../specs/nodes/GITVIEW-SPEC-0040.yaml); не считать дополнительный review record автоматически обязательным форматом или поддержанной функцией SpecGraph. |
| [0098](GITVIEW-SPEC-0098.yaml), [0108](GITVIEW-SPEC-0108.yaml) | Конкретные варианты GitHub App authorization и FSD setup composition. | Вернуться при выборе authorization и архитектуры. Успех, отмена и неопределённость подключения уже описаны на продуктовом уровне в [0058](../../specs/nodes/GITVIEW-SPEC-0058.yaml). |
| [0110](GITVIEW-SPEC-0110.yaml) | Возможная pure decision boundary для Today и варианты формулы. | Отложить интерфейс реализации и не выбирать неутверждённый creation alternative. Продуктовые условия и неопределённость закреплены в [0027](../../specs/nodes/GITVIEW-SPEC-0027.yaml), [0089](../../specs/nodes/GITVIEW-SPEC-0089.yaml) и [0102](../../specs/nodes/GITVIEW-SPEC-0102.yaml). |
| [0118](GITVIEW-SPEC-0118.yaml) | Доступная инспекция исторической точки и возврат. | Оставить черновиком после [исправления revocation](historical-accessible-point-revocation-correction-review-20261116.md); точные native controls и реальная accessibility требуют отдельной проверки. |
| [0120](GITVIEW-SPEC-0120.yaml) | Возможность pinch-перехода между областями навигации. | Сохранить как вариант, не обязательный first-version gesture. Pinch для density и доступный переход к объекту уже описаны в [0035](../../specs/nodes/GITVIEW-SPEC-0035.yaml) и [0075](../../specs/nodes/GITVIEW-SPEC-0075.yaml). |
| [0127](GITVIEW-SPEC-0127.yaml) | Критерий пользователя для первого автономного продуктового прояснения. | Использовать как рамку оценки, а не автоматически принимать весь граф или считать его evidence реализации. |

Это не полная семантическая классификация остальных черновиков. Новые продуктовые последствия и конфликты всё ещё могут потребовать отдельного узла или исправления существующего; технические и условные сценарии сохраняются для последующего этапа.
