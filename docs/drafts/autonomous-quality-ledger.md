# GitView: оценка автономного уточнения

Этот журнал сопровождает цель `conversation:gitview/excerpt-77`. Он фиксирует
наблюдаемые результаты и ограничения без числовой оценки качества, которую
имеющиеся проверки не подтверждают. Все спецификации в этом проходе остаются
`idea`, pre-canonical; app code и исполненные пользовательские тесты отсутствуют.

## Проход 1: первый запуск, обзор и возврат

Исходные узлы: 0003, 0005, 0007, 0012, 0019, 0022–0024. Сверены правила
хранения и неизвестных наблюдений, Project membership, фильтров и source access.
В 0022 предложены подтверждение непустого выбора, отдельные default Projects,
повтор после частичной ошибки и отмена до сохранения. В 0024 определён fallback
позиции по прежнему порядку, если исходный объект выпал из фильтра. В 0023
убрано не подтверждённое сроком утверждение о том, что успешно полученные
данные автоматически «current».

| Сценарий для проверки согласованности | Ожидаемое отношение к контрактам |
| --- | --- |
| Повторное подтверждение после частичного сохранения | 0022 не создаёт повторный default Project; другие memberships по 0005 сохраняются. |
| PR вышел из активного фильтра, пока открыт | 0007 сохраняет открытый обзор; при возврате 0024 сохраняет фильтр и выбирает соседний доступный anchor. |
| Issue загружены, PR refresh завершился ошибкой | 0003 сохраняет разные времена наблюдения; 0023 не выдаёт всю сводку за актуальную. |
| Временный offline и явный access denial | 0019 различает причины; 0023 и 0024 не показывают закрытые приватные данные при явном отказе. |

Это ручная сверка текстов и ожидаемых сценариев, а не выполненные тесты
приложения или автоматическое доказательство отсутствия противоречий. Новые
формулировки — самостоятельные решения агента; отдельного одобрения владельца
каждого поведения нет. Последующее изменение Project lifecycle или сортировки
может потребовать пересмотра соседних листьев.

Три изменённых candidate файла проверены `next-move --candidate-file`: `checked`
означает проверку YAML mapping, kind и соответствия имени/ID. Ссылки 24 узлов и
отсутствие циклов отдельно проверены для каждого типа ребра `refines` и
`depends_on`; это не семантическая проверка графа и не проверка смешанных циклов.
Остаются открытыми восстановление после повторного запуска, default Project
lifecycle, сортировка и точные правила полноты и свежести. Соответственно,
реализационная готовность ветви ещё не установлена.

## Проход 2: жизненный цикл Project

Обнаружен пробел между «один Project на Repository по умолчанию» в 0005 и
повторной настройкой в 0022: без явной связи с созданным default Project нельзя
отличить повтор от существующего пользовательского Project. Candidate 0025
предлагает отдельную локальную ассоциацию, отменяемые изменения, запрет пустого
сохранённого Project и сохранение других memberships при удалении. Это выбор
агента; как вести ассоциацию после удаления исходного Repository из Project
явно оставлено на предметную проверку. Он не добавляет ontology class.

Прежнее положение в этом журнале о lifecycle как полностью неопределённом
относится к состоянию до прохода 2. Решения 0025 ещё не доказаны проверкой
семантики или реального пользовательского поведения.

## Проход 3: наблюдения и частичные обновления

0026 уточняет 0003: успешная частичная страница может обновить наблюдавшийся
объект, но не доказывает отсутствия остальных и не сдвигает время последнего
полного наблюдения. Новое требование про порядок перекрывающихся запросов
запрещает заменять более новое уже принятое наблюдение заведомо более старым;
оно не утверждает, что порядок старта сам по себе доказывает свежесть данных.

Остаётся определить разрешение конфликтов для пересекающихся частичных scopes,
версий источника и изменения доступа во время запроса. Точный механизм пока не
выбран; описанные сценарии не демонстрируют работу базы или сети.

## Проход 4: Today и неопределённость

0027 предлагает проверяемое правило объединения условий Today и фильтров:
подтверждённое true в альтернативе достаточно для включения, неизвестный
filter input остаётся неизвестным, подтверждённое исключение не стирает
сохранённый объект. Добавлены сценарии для известного open при неизвестном
времени закрытия, неизвестного CI и смены часового пояса. Отображение
неопределённых кандидатов и исторических периодов остаётся незавершённым.

## Проход 5: проверки и review PR

0028 выделяет единицу текущего check, отдельные счётчики review и threads,
время и наблюдаемую ревизию, различие между нулём и отсутствием данных. Точные
GitHub status mappings, идентификация повторных запусков и представление частичных
счётчиков оставлены открытыми; выбранные примеры не доказывают соответствия API.

## Проход 6: сводки Project и портфеля

0029 уточняет независимые единицы, пересечение Projects, уникальность source
objects, частичное покрытие и различие текущего состояния и итогов периода.
Детализация UI, точные исторические метрики и представление покрытия остаются
открытыми; сценарии являются спецификацией, не измерением приложения.

## Самопроверка: исправлен конфликт default Project

Первый вариант 0025 сохранял default association после удаления из Project
связанного Repository. Тогда повторное подтверждение по 0022 возвращало бы
Project, в котором выбранного Repository нет. Это реальное противоречие между
авторскими черновиками, которое структурная проверка не обнаружила. Исправление:
сохранённое удаление соответствующего участника разрывает ассоциацию; повторное
явное подтверждение может создать новый default Project. Остальные участники,
Project ID и другие Projects сохраняются. Новый сценарий добавлен в 0025;
продуктовое решение остаётся предложением агента, а не одобрением владельца.

## Проход 7: история и графики

0030 различает snapshot, событие и отсутствие наблюдения; формулу burn-down и
его единицу не придумывает из смешанных PR и Issue. Для проверки качества
добавлены сценарии пропущенного дня, частичного Project и повторного закрытия
без истории. Это требования к наблюдаемому результату, не измеренный график.

## Проход 8: preview

0031 уточняет удержание source identity при перемещении ячеек, закрытие,
изменение фильтра и потерю доступа. Скользящий preview остаётся будущим
направлением; доступность, gesture arbitration и native поведение требуют
отдельной проверки на устройстве.

## Проход 9: доступность

0032 связывает доступные способы навигации с identity объекта и fallback из
0024, описывает различимость одноимённых номеров и отсутствие зависимости от
цвета, pinch и long press. VoiceOver и другие platform-проверки пока не
выполнялись: приложения и целевых device observations ещё нет.

## Проход 10: переход к источнику и sharing

0033 различает запрос на открытие от успешной загрузки и показ системного share
sheet от доставки; связывает ссылку с identity объекта и приватным доступом.
Поведение внешнего приложения, получателя и актуальность URL пока не проверены.

## Проход 11: описания PR и Issue

0034 отделяет исходный текст от извлечённых разделов и утверждений автора от
observed CI, вводит сценарий неоднозначных заголовков. Точная grammar parser и
установка шаблонов остаются отдельными нерешёнными темами.

## Проход 12: масштаб сетки

0035 отделяет изменение плотности от навигации и обновления источника, связывает
anchor с identity и явными фильтрами, описывает одновременный refresh и
доступную альтернативу pinch. Реализация native gesture и производительность
не проверялись.

## Проход 13: доступ и сохранённые наблюдения

0036 связывает offline, явный отказ, 404, disconnect и повторное подключение с
уже выбранной рабочей политикой приватного кэша. Неизвестные свойства source
ответов, порядок конкурентных событий и UX удаления данных остались открыты;
сама политика является предложением агента и не проверена приложением.

## Проход 14: конкурирующие обновления и доступ

0037 уточняет границу из 0026/0036: порядок начала или завершения запросов сам
по себе не доказывает свежесть source values; неоднозначный результат не создаёт
ложный полный snapshot. Ответ, пришедший после explicit denial или disconnect,
сам по себе не восстанавливает доступ к приватному кэшу. Механизмы сравнения
источника и фактическая модель конкурентности остаются открытыми.

## Проход 15: неполная identity Repository

0038 уточняет применение принятого правила numeric REST ID к отсутствующему ID,
переиспользованному адресу и несортируемым наблюдениям. Совпадение имени не
переносит историю и memberships; вопросы cross-instance и миграции ID остаются
открытыми. Отношение GitHub к Repository не переопределялось.

## Проход 16: свойства и связи Issue

0039 сверяет утверждённый набор полей Issue с различиями между mentions и
closing links, source roles, discussion counters и direct sub-issues. Закрытие
не приравнивается к успешному выполнению; PR review threads не переносятся на
Issue. Доступность отдельных полей через GitHub ещё не подтверждена.

## Проход 17: тестируемость и evidence

0040 уточняет непосредственно запрошенные владельцем DI, TDD и network/data
test doubles. Изолированная проверка, реальные адаптеры и device evidence
различаются; выбранные тестовые инструменты и реализация ещё отсутствуют.

## Проход 18: свойства и счётчики PR

0041 сверяет выбранные владельцем группы A–G с состоянием, ролями, числовыми
счётчиками и временем источника. Оценка review и CI остаются независимыми,
индивидуальный diff и thread content не добавлены. Mapping полей и revision
association ещё не проверены на API.

## Проход 19: порядок и неопределённые кандидаты

0042 предлагает детерминированный порядок по source update time и отдельную
доступность uncertain candidates, чтобы закрыть часть пробелов 0024/0027.
Порядок является решением агента, не выбором владельца; точный UI и source
timestamp mapping остаются открытыми.

Повторная сверка выявила несогласованность между безусловным обещанием «объект
один раз» в 0007/0027 и допустимыми записями без подтверждённой identity в 0042.
Уточнено: дедупликация гарантирована для подтверждённого source identity;
неразрешённое совпадение записей не объявляется ни точным числом разных
объектов, ни доказанным совпадением по имени. Добавлен сценарий в 0027.

## Проход 20: холодный запуск и возврат в сессию

0024 предлагает на холодном запуске открывать обзор Projects, а при сохранённой
сессии iOS восстанавливать допустимый контекст по возможности. Это решение
агента согласовано с 0004, но не выбрано владельцем напрямую. Граница между
сценами iOS, временем жизни процесса и допустимостью контекста ещё требует
platform review; это не свидетельство поведения приложения.

## Проход 21: сквозные сценарии

0043 связывает несколько ветвей в сценариях настройки, пересечения Projects,
завершения работы, preview и отказа доступа. Это проверяемые ожидания, а не
запущенные тесты; source mapping и device fixtures остаются открытыми.

## Проход 22: независимые свойства наблюдения

0044 разделяет сохранённые факты, покрытие, время наблюдения, результат запроса
и доступ к приватным данным. Это позволяет выразить «последний известный
пустой список и ошибка нового refresh» без противоречивого общего статуса.
Модель local-state является предложением для спецификаций, не новой онтологией.

## Самопроверка: время частичного и полного наблюдения

Неоднозначная формулировка 0003 о том, что прерванное обновление не продвигает
время успеха, могла противоречить 0026/0044, где отдельно успешно наблюдённый
объект получает своё время в частично загруженном scope. Уточнено: не двигается
время последнего **полного** наблюдения scope; действительно принятый факт может
иметь собственное время, при этом покрытие остаётся неполным. Это исправление
согласованности текста, а не доказательство поведения хранилища.

## Проход 23: частичное сохранение выбора

0045 определяет per-repository исходы подтверждения, частичный успех, повтор,
отмену во время сохранения и изменение доступа. Он не утверждает атомарность
всего batch и не считает неизвестный in-flight результат неудачей. Механизм
идемпотентности после завершения процесса остаётся открытым.

После аудита 0025 узел 0052 предложил атомарную видимость пары Project и default
association, чтение durable конфигурации при повторе и явный unknown, если
исход не определён. Это не решает механизм конкурентного позднего commit и
не является доказательством реального crash recovery.
Позже добавлено наблюдаемое требование единственности default association при
конкурирующих и поздних commits. Механизм гарантии и реальные execution evidence
по-прежнему не установлены.

## Проход 24: агрегаты и устаревшие данные

0046 различает подтверждённый итог и сумму ранее наблюдавшихся значений.
Особый случай: вчерашние три открытых PR не доказывают, что сейчас открыто
минимум три. Также ограниченный доступ к приватному Repository учитывается
при показе производных счётчиков, а не только исходных карточек.
Первый `next-move` отклонил YAML из-за двоеточия внутри некавыченной строки;
формулировка исправлена и проверка повторена. Это ошибка авторского формата,
а не обнаруженное противоречие предметной модели.

## Проход 25: общий экран Projects

0047 связывает главную коллекцию Projects с отдельными units счётчиков,
переходом по сигналу и сохранением доступности и coverage. Конкретный layout и
порядок Projects не утверждаются на основании прототипа внутри одного Project.

Повторная межветвовая сверка обнаружила конфликт с приватным кэшем: default
Project может получить название из приватного Repository, но прежняя формулировка
требовала всегда показывать это имя. 0004 и 0047 уточнены: Project остаётся
представлен без раскрытия запрещённого source-derived имени; классификация
пользовательских и source-derived имён остаётся открытой. Это исправление
авторского противоречия, а не подтверждение работающего контроля доступа.

## Проход 26: триггеры обновления

0048 уточняет manual, foreground и opportunistic background refresh через
наблюдаемые scope и outcome. Он не задаёт частоту, размер страниц, конкретный
endpoint или гарантии планировщика iOS; эти технические решения остаются открыты.

## Проход 27: граница Today

0049 уточняет смену локального дня и часового пояса при открытом preview,
сохранение filters и отсутствие достаточного охвата новой даты. Историческая
группировка и конкретный UI при активном жесте остаются открытыми.

После readiness-аудита для 0049 предложено не переставлять сетку посреди
активного жеста и показывать, что прежняя раскладка ещё не отражает новый день;
native accessibility и способы индикации остаются непроверенными.
Также уточнён обязательный состав охвата: retrieval только созданных сегодня
объектов не подтверждает отсутствие ранее открытой работы. Способ доказать
полноту по source API намеренно остаётся открытым.

## Проход 28: состав preview

0050 уточняет минимальный содержательный набор для Project, Repository, PR и
Issue, сохраняя запрет выводить restricted private details. Точные размеры,
визуальный приоритет полей и native accessibility остаются предметом UX review.

## Проход 29: распознавание разделов

0051 предлагает узкий профиль для точных заголовков существующих шаблонов,
сохраняет исходный текст и различает отсутствующий, пустой и неоднозначный
раздел. Предложение не объявляет поддержку всего Markdown и не означает, что
шаблоны установлены в GitHub-репозиториях. Обработка неоднозначных delimiters
и будущих версий профиля остаётся открытой.
Позднее уточнены локальные правила границ heading и поддерживаемых fence
markers; это специально ограниченный профиль, не заявление о полном Markdown
или проверенная реализация parser.

## Проход 30: ontology gap действия удаления

Сопоставление lifecycle Project с выбранной онтологией выявило: `AddRepository`
объявлен как action, а удаление члена Project требуется 0005/0025, но отдельного
действия для него в draft.5 нет. Подготовлен [непринятый candidate](../../ontology/review/remove-repository-action-candidate.md)
с вопросом о необходимости action и семантике снятия membership. Package и
context не менялись; absence relation не утверждается как action event.

## Проход 31: конфликтующие наблюдения

0053 уточняет, что несравнимые противоречивые значения не выбираются по
порядку прихода и не превращаются в подтверждённый current state. Условия
сопоставимости и безопасного разрешения конфликта описаны на уровне результатов;
source-specific evidence и способ хранения кандидатов остаются открытыми.

Сверка 0023 с 0036 уточнила, что показ предыдущих значений после временной
ошибки относится только к данным, разрешённым к отображению. Само сохранение
ранее полученных записей не отменяет restriction после explicit access denial.

## Самопроверка: acceptance для будущего preview

В 0015 будущий sliding preview стоял в общем списке acceptance рядом с
требованиями первой версии, хотя 0020 относит его к позднему объёму. Будущий
критерий перенесён в `future_acceptance_candidates`; сам сценарий сохранён как
future и не объявляется выполненным. Это устранение неоднозначности scope,
не отмена будущей идеи пользователя.
