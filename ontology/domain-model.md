# GitView: консолидированная предметная модель

Содержательный черновик. Формулировки агента и открытые решения указаны
отдельно. Рабочий compiler package выбран в
[`specgraph.project.yaml`](../specgraph.project.yaml).
Текущий выбор — [draft.5](candidates/domain-v0.2.0-draft.5/README.md);
технические описания пакета 0.1 и промежуточных кандидатов ниже относятся к
истории работы. Типизированная ссылка действия и правила состава теперь
проверены в draft.5; смысловые и технические gaps по-прежнему видны.

Роль онтологии — удерживать значения терминов, свойства и отношения, которыми
оперируют спецификации. Жесты, кнопки и значки не становятся сущностями только
потому, что появились в макете (`excerpt-17`, текущий приоритет `excerpt-52`).

## Понятия, отдельно от свойств

| Понятие | Смысл и статус | Отдельная граница |
| --- | --- | --- |
| GitView | Продукт и единый корень пользовательской композиции HC. | Не обязан становиться DomainEntity ради экспорта. |
| User | **Оператор GitView**, подтверждено в `excerpt-53-reply`. | GitHub-идентичности отдельно; идентичность/свойства оператора ещё не определены. |
| Project | Проект GitView; состав репозиториев задаётся отдельным правилом. | Не тождественен GitHub Project. |
| Code | Пользовательская формулировка: по сути папка с файлами. | Границы истории/worktree и идентичность открыты; не моделируем всю файловую систему. |
| VersionControlSystem | Система, действующая над Code; пример — Git. | Имя системы не доказывает факт конкретного действия. |
| Repository | Пользовательская формулировка: Code, в котором действует система контроля версий. | Членство в Project и управление GitHub не смешиваются с определением. |
| GitHub | В обсуждённом контексте актор управления Repository. | Роль в действии отделена от постоянного типа каждого участия. |
| GitHubRepository | Repository в отношении управления со стороны GitHub. | Смысл согласован; в рабочем draft.5 предложен contextual protocol над тем же Repository, окончательное принятие представления не установлено. Не придумываем второй объект и ID ради имени. |
| PullRequest | Связан с предлагаемыми изменениями; в примере владельца — последствие действия. | Поля выбраны; кандидатное определение «запрос на рассмотрение/включение изменений» отдельно не утверждено. PR не означает merge. |
| Issue | Объект источника; в обсуждённой цепочке может выступать мотивом для актора. | Поля выбраны; общая формулировка «вопрос, проблема или запрос на работу» пока кандидатная. |
| ReviewThread | Обсуждение в контексте review PR. | Выбраны счётчики, не содержимое; длительность и незакрытость различаются. |
| CIStatus | Рабочее имя агента для наблюдаемого состояния проверок. | Выбрана сводка актуальных отдельных проверок PR по образцу GitHub; точный смысл класса открыт. |
| Metric | Рабочее обозначение измерения для обзора. | Нужны область, единица, время и полнота каждого показателя; общий динамический суперкласс не принят. |

Activity остаётся гипотезой о действиях, не самостоятельной сущностью.
Organization — метаданные; Group сейчас избыточен. GitManagementSystem,
ManagedRepository и другие провайдеры отложены. Branch, label, Issue type,
milestone и участники источника не получают новые классы автоматически.

Источники: `excerpt-10`–`excerpt-25`, исправленный HC `excerpt-30`, управление
и аналогия Decorator `excerpt-31`–`excerpt-32`, User `excerpt-53-reply`.

## Выбранные свойства и состояния

### Project

Локальный ID, название, необязательное описание, состав репозиториев.
Состав: один или несколько; репозиторий может входить в несколько проектов;
по умолчанию один проект на один репозиторий. Разные organizations допустимы.
[Согласованный состав](../docs/drafts/project-summary-proposal.md), `excerpt-41`.

Сводка — вычисляемое представление состава: охват данных, PR/draft и Issue,
review/CI/треды/blockers, результаты за период, графики при наличии истории.
Общий итог портфеля учитывает пересечения, а не складывает итоги проектов.
Механика создания, изменения состава и ошибки ещё требует спецификации.

### PullRequest

- ID источника, номер внутри репозитория, название, описание, URL.
- Открыт / закрыт без merge / merged; draft отдельно; labels отдельно.
- GitHubRepository, исходная/целевая ветки, текущая ревизия; создатель,
  запрошенные reviewers, связанные Issue.
- Итоговая оценка review источника; число тредов всего и незакрытых.
- Число красных, жёлтых, зелёных и всех актуальных отдельных проверок.
- Добавленные/удалённые строки раздельно, число файлов и коммитов.
- Создание/обновление, закрытие/merge при применимости, время и источник наблюдения.
- Описание: Problem, Motivation, Expected outcome, Changes, Validation, References.

[Выбраны 24 пункта](../docs/drafts/pull-request-ontology-options.md),
`excerpt-34`, `excerpt-35-reply`, `excerpt-38`. Это не число атомарных полей.
Типы, nullable/unknown и source bindings ещё требуют определения.

### Issue

- ID источника, номер внутри репозитория, название, описание, URL.
- Открыта / закрыта; причина состояния, labels и Issue type при наличии.
- GitHubRepository, создатель, assignees.
- Связанные PR с различением closing link и упоминания; parent/sub-issues,
  блокирующие/блокируемые Issue, milestone.
- Число комментариев и участников; непосредственных sub-issues всего и закрытых.
- Создание/обновление, закрытие при применимости, наблюдение и его источник,
  последний комментарий при наличии.
- Описание: Problem, Motivation, Expected outcome, References.

[Все 23 пункта выбраны](../docs/drafts/issue-ontology-options.md), `excerpt-38`.
Комментарии Issue не равны ReviewThread. Закрытие не обязательно выполнение;
assignee не доказывает начало работы; обновление не обязательно комментарий.
Доля закрытых sub-issues не объявляется долей выполненной работы.

### Исходное, наблюдаемое и вычисляемое

Итог review и счётчики тредов — разные свойства. Их визуальные отметки пока
предложение отображения; проверка значков отложена по `excerpt-52`.
Для CI открыты единица проверки, релевантная ревизия/попытка, особые состояния
и неполнота. Ориентир GitHub не равен доказанной эквивалентности поведения.

Для Metric нужны измеряемый набор, единица и временная область. Текущие
счётчики и результаты за период различаются. Unknown не равен нулю, текущие
данные не доказывают историю. Правила свежести и подсчёта относятся к specs.
Уточнение смысловой границы и примеры подготовлены как [кандидат для review](review/metric-meaning-candidate.md);
они не изменяют выбранный package и не вводят class для каждого графика.

Problem — исходная проблема; Motivation — заявленная причина; Expected outcome —
ожидание; Changes — предложенные изменения; Validation — заявление о проверках;
References — источники. Это свойства содержания, не шесть новых сущностей.
Текст Motivation сохраняется с источником и не доказывает мотив всех участников.
Validation не заменяет CI; Expected outcome не подтверждает достижение результата.

## Связи, отношения, роли и действия

| Связь/отношение | Установлено | Что не выводим автоматически |
| --- | --- | --- |
| Project ↔ Repository | Состав и повторное использование. | Простую сумму итогов проектов; детали действия изменения состава. |
| VCS → Code | Система действует над кодом. | Факт выполненного действия из наличия декларации. |
| GitHub → Repository | `RegisterRepository` устанавливает `managesRepository`; тот же Repository выступает в роли GitHubRepository. | Наследование, второй Repository или обязательный программный Decorator. |
| PR / Issue → GitHubRepository | Выбран исходный контекст принадлежности. | Organization как обязательную границу Project. |
| PR ↔ Issue | Выбраны ссылки с разными смыслами. | Причинность и мотив конкретного актора только из ссылки. |
| Issue ↔ Issue | Иерархия и блокировки. | Их взаимозаменяемость; открытость blocker при неизвестных данных. |
| Объект ↔ участник | Автор, reviewer, assignee — роли/ссылки. | Равенство оператору User или доказанное участие в изменении Code. |

В пользовательском смысле отношение — свойство, возникающее через действие
актора над объектом; общая ссылка менее конкретна. Это сохраняется даже если
compiler schema называет обе технические декларации `relations`.

### Управление репозиторием со стороны GitHub

GitHub регистрирует Repository у себя действием `RegisterRepository` и начинает
обслуживать его как репозиторий GitHub. Возникает отношение `managesRepository`,
в котором тот же Repository выступает в роли `GitHubRepository`
(`conversation:gitview/excerpt-58-reply`).

- При создании репозитория на GitHub модель устанавливает `managesRepository`
  в момент регистрации. [GitHub REST API](https://docs.github.com/en/rest/repos/repos#create-a-repository-for-the-authenticated-user)
- При transfer внутри GitHub, когда источник подтверждает тот же объект,
  управление сохраняется. Меняется владелец, сохраняются история и членство
  Repository в Projects. [Решение об идентичности](review/repository-identity.md)

Чтение API наблюдает текущий объект. Способ связать наблюдение с событием
регистрации и момент окончания управления остаются открытыми.
В [рабочем draft.4](candidates/domain-v0.2.0-draft.4/README.md) действие
задано в декларации `managesRepository`. Правило непрерывности оформлено
отдельным [черновиком спецификации](../docs/drafts/GITVIEW-SPEC-0002.yaml).

### Мотив и последствия

Установленный пример: Issue — мотив для актора; актор меняет Code; PR назван
последствием. Изменение Code и публикация PR могут потребовать разных границ
и наблюдений; полная causal chain из одних ссылок не конструируется.

Ограниченный пример **агента для уточнения**, не принятое действие: User
добавляет Repository r2 в Project P, используя GitView как инструмент.
При том же ID Project: до состав `{r1}`, после успеха `{r1, r2}`; изменился
состав, не исходный Repository или его владелец. Мотив без источника неизвестен.
Повторное добавление, ошибка записи и удаление последнего репозитория требуют
правил. Это модельный пример, не observed event и не выполненный тест.

## Историческая техническая привязка 0.1.0

Контрольный пакет 0.1.0: 10 классов, 2 candidate relations, 0 локальных полей.
GitView/User/GitHubRepository ещё не связаны с классами пакета; не все обязаны
становиться DomainEntity. Opt-in 0.2.0-pilot.1 с motivation-core 0.1.0 и
events-core 0.2.0 был отдельным draft-контекстом на том этапе; текущий выбор
указан в начале документа и [обновлённом аудите](review/completeness.md).

Далее: сверить смыслы и gaps из [матрицы полноты](review/completeness.md),
типизировать свойства и связи, подготовить versioned compiler candidate,
проверить tooling, согласованно обновить IR/selection/HC-HCS. Только после
этого — материализация spec graph. Каждый spec ссылается на определённые
термины или явно сохраняет unresolved gap. UI-полировка не условие перехода.

Ссылки excerpt — локальные фрагменты, не удостоверенные ID сообщений.

## Решение identity — 2026-11-03

Пользователь выбрал A (`excerpt-54-reply`): если источник подтверждает тот же
GitHub-объект, rename и transfer сохраняют один Repository, его историю и
членство в Projects. Конкретный API ID, encoding/storage и alias handling не
выбраны этим ответом. См. [decision review](review/repository-identity.md) и
[draft.2](candidates/domain-v0.2.0-draft.2/README.md). Предыдущая формулировка
об открытом identity-вопросе относится к более ранней итерации.

GitView в glossary остаётся названием продукта, не обязательным новым entity
class. Motive определён в общем пакете, но намеренно не выбран в foundation.
[Разбор происхождения findings](review/remaining-findings.md) не заменяет
принятие всего package или materialization spec graph.

## Исполняемое отношение оператора

В [draft.3](candidates/domain-v0.2.0-draft.3/README.md) GitView описывает `User` как экземпляр оператора приложения. В позиции `subject` стоит этот же участник, а `object` — конкретный `Project`. В проверенном примере `AddRepository` несёт ссылку на существующий `Repository` и изменяет состав только выбранного проекта. Это уточняет техническое представление `User` из draft.2. Правила входа, хранения идентичности и повторного добавления по-прежнему открыты.
