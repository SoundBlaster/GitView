# GitView — предметная карта для графа спецификаций

Эта карта объединяет обсуждённые смыслы и показывает их представление в
выбранном `local.gitview.domain@0.2.0-draft-composition.5`. Она не заменяет
исходный package и не утверждает, что все нужные типы уже формализованы.
Утверждённые пользователем направления используются как основа графа;
точность технических bindings и отдельных границ ещё уточняется.

## Композиция для чтения

```text
GitView — приложение / граница продукта
├── User — оператор приложения
└── Project — проект GitView
    └── GitHubRepository — контекстная роль Repository
        ├── Repository
        │   ├── Code
        │   └── VersionControlSystem
        └── GitHub
            ├── Issue
            ├── PullRequest
            ├── ReviewThread
            ├── CIStatus
            └── Metric
```

Это композиция из обсуждения, не дерево наследования и не список всех
отношений. Названия GitView и GitHub здесь не означают, что Issue является
частью экземпляра GitHub в смысле формальной композиции. UI, preview, карточка,
фильтр, сводка и график описываются спецификациями, а не объявляются
предметными сущностями только из-за присутствия в интерфейсе.

| Понятие | Смысл и граница | Выбранный package / использование |
| --- | --- | --- |
| GitView | Приложение для обзора, не замена GitHub. | Граница продукта, не объявленный класс. |
| User | Оператор GitView; автор, reviewer и assignee в GitHub не обязательно тот же участник. | `gitview:User`; авторизация и связывание identities не определены. |
| Project | Локальный проект GitView с названием и устойчивой идентичностью. Состав — отдельно. | `gitview:Project`; не GitHub Projects. |
| Code | Код, в рабочей формулировке — папка с файлами. | `gitview:Code`; точная граница открыта. |
| VersionControlSystem | Система, действующая над кодом для управления версиями; Git — пример. | `gitview:VersionControlSystem`. |
| Repository | Код, в котором действует система контроля версий. | `gitview:Repository`; identity при подтверждённом rename/transfer сохраняется. |
| GitHub | GitHub как источник данных и участник управления repository. | `gitview:GitHub`. |
| GitHubRepository | Тот же Repository в контексте управления GitHub. | Контекстный `gitview:GitHubRepository` protocol, не второй Repository и не subclass. |
| PullRequest | GitHub PR, связанный с предлагаемыми изменениями кода. | `gitview:PullRequest`; создание не означает merge. |
| Issue | Зафиксированный в GitHub вопрос, проблема или запрос на работу. | `gitview:Issue`; формулировка значения остаётся кандидатной. |
| ReviewThread | Тред обсуждения review; предмет обзора — счётчики. | `gitview:ReviewThread`; содержание внутрь первой версии не входит. |
| CIStatus | Наблюдаемое состояние CI. | `gitview:CIStatus`; гранулярность одной проверки или агрегата и mapping специальных состояний открыты. |
| Metric | Измерение с определёнными областью, единицей и периодом. | `gitview:Metric`; правила каждого показателя в specs. |
| Motive | Возможный мотив действия участника. | Заимствованный `motivcore:Motive`; ссылка Issue–PR не доказывает мотив. |

## Отношения, действия и связи

- `GitHub → RegisterRepository → Repository`: действие устанавливает
  `managesRepository`; Repository выступает как GitHubRepository в этом контексте.
- `User → AddRepository(repository) → Project`: добавление существующего
  Repository меняет состав Project; один Repository может входить в несколько
  Projects. В draft.5 поле действия — обязательный typed `Ref<Repository>`;
  приложение отвечает за разрешение ссылки и проверку существования объекта.
- Project содержит один или более репозиториев; по умолчанию одному Repository
  соответствует один Project. Organizations — метаданные источника, и Project
  может охватывать разные organizations.
- PR и Issue имеют контекст Repository. Связи PR–Issue, parent/sub-issue и
  blocker — предоставленные источником связи; они не устанавливают действие
  актора или его причинный мотив.
- Владелец описал возможную цепочку: актор действует над Code под мотивом,
  связанным с Issue, и следствием может быть PR. Это не утверждение о каждой
  связанной паре Issue и PR.
- `versionControlsCode` существует как декларация связи; порождающее действие
  и возникающее свойство ещё не определены. Не выдаём его за завершённое
  actor/action model.

## Свойства и наблюдения

Выбранные наборы PR и Issue сохранены в
[0008](../../docs/drafts/GITVIEW-SPEC-0008.yaml) и
[0009](../../docs/drafts/GITVIEW-SPEC-0009.yaml), подробные исходные списки —
в документах `pull-request-ontology-options.md` и
`issue-ontology-options.md`. В package уже есть часть scalar fields и links;
коллекции участников, идентичности, ссылки, время и availability выражены не
полностью. Это gap технической модели, а не повод терять требования из specs.

Доступные, отсутствующие, неизвестные, устаревшие и неполные данные различаются.
CI, review и незакрытые треды — отдельные сигналы; неизвестное не равно нулю
или одобрению. Сводка и график — вычисленные представления наблюдений, а не
новое исходное состояние GitHub.

## Намеренно не введено

`Group` избыточна рядом с Project; generalized management system и другие
провайдеры отложены. `Activity` пока гипотеза о действиях, не отдельная
согласованная entity. Нет автоматического вывода причины, успешного результата,
merge readiness или исторического ряда из одной ссылки, review или snapshot.

Структурная проверка выбранной композиции проверяет разрешение и согласованность
артефактов, а не истинность модели. Источники и оставшиеся gaps:
[domain-model](../domain-model.md), [completeness](completeness.md),
[draft.5](../candidates/domain-v0.2.0-draft.5/README.md) и
[дерево спецификаций](../../docs/drafts/specification-graph.md).
