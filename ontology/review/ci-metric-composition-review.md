# CIStatus и Metric: проверка композиции спецификаций

Пакет draft.6 содержал общие value objects `CIStatus` и `Metric`,
но не устанавливал гранулярность CIStatus и не формализовал поля измерения.
Впоследствии выбран рабочий draft.7 с предложенным уточнением CIStatus.
Уточнения ниже — анализ кандидатов, не семантическое утверждение package.

| Наблюдение | Допустимое утверждение | Не следует автоматически |
| --- | --- | --- |
| Одна current check с source failure и известной revision | Есть наблюдаемая проблема для этой check и revision | Все проверки завершены, PR нельзя влить или провалился тест |
| Набор отдельных current checks | Можно вычислить показатели по известной классификации и coverage | Один `CIStatus` уже типизирован как эта сводка |
| Пять failed checks на двух PR | Две разные величины: checks и затронутые PR | Пять PR или семь независимых проблем |
| Известная оценка review и число unresolved threads | Два самостоятельных значения | Вывод одного из другого или определение статуса CI |
| Один показатель за период и другой snapshot | Каждое измерение имеет свои единицу, основание и время | Их можно складывать или представлять одним одновременным snapshot |

Рекомендация для дальнейшего ontology review: предпочесть значение состояния
одной source-confirmed check в заданном контексте как узкий смысл CIStatus,
а сводку счётчиков определить в specs как результат классификации отдельных
наблюдений. Это не доказывает, что единственный источник CI обязательно есть
GitHub check run: commit-status context остаётся отдельным семейством. Решение
применено в рабочем draft.7 после [сверки потребителей](ci-status-consumer-audit.md);
семантическое утверждение и реальный source mapping не установлены.

Предложенный смысл Metric — результат измерения с интерпретируемой величиной,
единицей, scope и временем; необходимые конкретному утверждению evidence и
coverage остаются частью контекста. Это не делает CIStatus автоматически Metric,
а подсчёт checks — новой domain entity или action-derived отношением. См.
[кандидат Metric](metric-meaning-candidate.md) и
[границы CI/review](ci-review-boundaries-candidate.md).

При классификации конфликтующие неупорядоченные observations одной и той же
check нельзя сложить как два отдельных результата или молча выбрать актуальный.
Это уточнено в [0061](../../docs/drafts/GITVIEW-SPEC-0061.yaml); сквозные
границы времени и conflict описаны в 0046 и 0053. Эти сценарии не выполнялись
на GitHub или iOS; source mapping и независимое semantic review не установлены.
