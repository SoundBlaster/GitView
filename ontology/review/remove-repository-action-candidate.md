# Candidate: удаление Repository из Project

Дополнение 14 ноября: подготовлен изолированный [draft.6](../candidates/domain-v0.2.0-draft.6/README.md)
с минимальным действием и проверкой SDK-потребителя. После пилота рабочей
selection выбран draft.6; компиляция, тестовый обработчик и проверка словаря не утверждают
смысл нового действия и не доказывают фактическое выполнение в GitView.

Статус: **историческое содержательное предложение для review**. Действие добавлено
в draft.6 и присутствует в текущем рабочем draft.12; ни выбор пакета, ни это
предложение не являются semantic approval или доказательством выполненного действия. Источники —
[состав Project](../../docs/drafts/GITVIEW-SPEC-0005.yaml),
[жизненный цикл Project](../../docs/drafts/GITVIEW-SPEC-0025.yaml) и
[исторический draft.5](../candidates/domain-v0.2.0-draft.5/composition/domain-ontology-package.yaml).

## Зачем

В draft.5 действие `AddRepository` уже описывает оператора `User`, объект
`Project` и параметр-ссылку на существующий `Repository`. Спецификация 0005
также требует удаления членства из одного Project без удаления исходного
Repository или изменения других Projects. В пакете отдельного действия для
этого случая нет. Это **gap для рассмотрения**, а не доказательство, что каждую
UI-команду необходимо формально моделировать в онтологии.

## Ограниченный вариант агента

```text
User ── RemoveRepository(repository: Ref<Repository>) ──▶ Project
```

- `User` — оператор GitView в конкретном действии, не автоматически автор PR.
- `Project` — объект изменения, сохраняющий local identity.
- `repository` — ссылка на конкретный существующий Repository; совпадение имени
  не является доказательством identity.
- При успешном действии соответствующий Repository больше не входит в этот
  Project; другие Projects, Repository на GitHub и его история не удаляются.
- Сохранённый Project должен сохранять хотя бы один Repository. Действие,
  которое нарушило бы это условие, не устанавливает успешное новое состояние;
  детали UI и обработки ошибок принадлежат спецификации.

Пример для проверки смысла: до действия `P = {R1, R2}`, `Q = {R1}`; оператор
удаляет `R1` из `P`; после подтверждённого успеха `P = {R2}`, `Q = {R1}`, а
source Repository `R1` существует как прежде. Это пример ожидаемого состояния,
не наблюдение реального действия или свидетельство его выполнения.

## Открытые вопросы

1. Нужно ли вводить отдельное named action в онтологии для данного устойчивого
   предметного изменения, или достаточно использовать общий механизм изменения
   состава в specs? Простая симметрия с `AddRepository` сама по себе не причина.
2. Как в формализме описать снятие ранее существовавшего membership и его
   последствия, не превращая source link или историю операции в неявное
   постоянное actor-derived отношение? Имя и lifetime такого отношения не
   выбраны.
3. В 0025 предложено разрывать default association, если удалён связанный
   исходный Repository. Это локальная продуктовая политика; нужно ли ей место
   в ontology package либо достаточно спецификации, пока не решено.
4. Поведение при повторном удалении, конкурентном изменении состава и отказе
   хранилища нуждается в уточнении product specs. Нельзя выводить факт успеха
   или намерение актора из отсутствия membership в одном наблюдении.

На момент первоначального review package и selection сохранялись без изменений.
Последующее [решение о рабочем draft.6](draft6-working-context-decision.md)
не утверждает формальное состояние онтологии; прежние links и действия сохранены.

## Смысловая проверка против действующего контракта

| Ситуация | Ожидаемый результат | Чего нельзя заключать |
| --- | --- | --- |
| `P = {R1, R2}`, `Q = {R1}`; удалить `R1` из `P` | При подтверждённом успехе `P = {R2}`, `Q = {R1}`; identities сохраняются. | Что `R1` удалён в GitHub или перестал входить в `Q`. |
| `P = {R1}`; удалить последнего участника | По рабочей политике 0025 изменение не сохраняется. | Что попытка успешна или Project удалён. |
| Membership не наблюдается в неполном локальном состоянии | Результат по одному отсутствию записи не подтверждён. | Кто действовал, было ли действие и успешно ли оно завершилось. |
| `P` удалён целиком | Это отдельная операция жизненного цикла Project. | Удаление исходных Repositories или изменение других Projects. |

При успешном удалении прекращается принадлежность `R1` к `P`; свидетельство
истории и актуальная membership — разные факты. Имя action не требует создавать
постоянное свойство «удалён из». Формализация изменения membership и её
validity во времени остаётся открытой. Снятие default association при удалении
связанного Repository — локальная политика 0025, не неотъемлемый смысл всякого
удаления membership. Модельные проверки в [аудите 0025](../../docs/drafts/leaf-readiness-0025.md)
не являются реальным выполнением действия.
