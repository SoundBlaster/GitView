# CIStatus и review: кандидат смысловых границ

**Рабочий контекст на 15 ноября:** выбранный `draft.12` уточняет `CIStatus`
как наблюдаемое состояние одной status-check entry, а не сводку проверок.
Корневой 0001 и 0060–0061 используют ту же рабочую границу: entry, её состояние
и числовой count различаются. Формальная типизация, исходные данные и semantic
approval остаются непроверенными. Последующая таблица и открытый вопрос о выборе
гранулярности фиксируют исторический контекст draft.5; это не текущий выбор.

Статус: **предложение для review**, не принятое определение. В выбранном
`local.gitview.domain@0.2.0-draft-composition.5` (`draft`) `CIStatus` объявлен
как `ont:ValueObject`, а `ReviewThread` — как `ont:DomainEntity`. Отдельного
класса для review assessment в пакете нет; свойство `reviewAssessment` пока
типизировано строкой у `PullRequest`. Этот документ не изменяет пакет.

## Раздельные значения

| Понятие или факт | Рабочий смысл | Граница |
| --- | --- | --- |
| `CIStatus` | Наблюдаемое состояние проверки CI либо её представленной сводки в заданном контексте. | Пока открыто, должен ли термин означать состояние одной проверки или только агрегата; `draft.5` сам этого не разрешает. |
| Check counts | Измерения числа актуальных отдельных PR checks по выбранной классификации и общего числа. | Не число workflow runs, исторических попыток или отдельных PR; не все состояния обязаны попадать в три цвета. |
| Review assessment | Предоставленная источником оценка review для PR. | Не выводится из числа threads, CI, одного значка или имени оператора GitView. |
| `ReviewThread` | Тред обсуждения в контексте review PR. | Содержимое отдельного треда сейчас вне выбранного обзора; unresolved и длительность — разные признаки. |
| Thread counts | Число всех и число unresolved review threads в заявленном scope наблюдения. | Не Issue comments, не assessment и не доказательство того, что все замечания решены. |

Всё это относится к PR-контексту, но такое использование не задаёт определения
термина только через экран или родительский объект. Важно сохранять источник,
применимую revision, время и coverage там, где без них утверждение теряет
смысл. Эти контекстные свойства не являются автоматически новыми ontology
entities или доказанными API-полями.

## Примеры для проверки смысла

1. В выборке известна одна failed check, а остальные не загружены: есть
   положительное свидетельство в контексте этой revision, но полный count и
   отсутствие других проблем не доказаны.
2. Известны ноль unresolved threads и отдельный source assessment «changes
   requested»: значения сосуществуют, ни одно не должно перезаписывать другое.
3. Тред unresolved не обязательно долгий; «долгий» требует основания и
   отдельной временной политики, а не выводится только из открытого состояния.
4. Полученный ранее зелёный статус не доказывает успешные проверки новой
   revision. Отсутствующий status не равен zero или success.

Это смысловые примеры, не результаты запросов или tests. В первой версии
выбраны счётчики CI и threads; они не требуют отображать содержимое проверок
или тредов. Символы и цвета — presentation, а не новые состояния онтологии.

## Исторические открытые решения draft.5

- Для `CIStatus` нужно отдельно решить гранулярность: одно состояние проверки,
  aggregate или ограниченное семейство значений. Нельзя делать вид, что
  существующая общая строка package уже выбрала один из вариантов.
- Источники и семантика «актуальной» проверки, retries, association с revision,
  special conclusions и полноты будут определены отдельно с evidence. Здесь
  не предполагается конкретная схема GitHub API.
- Review assessment и thread counts независимы; действие reviewer и порождённое
  им отношение нельзя вывести только из счётчика или сопоставления цветов.
  Дополнительный `Review` class, `Check` entity и action не вводятся до
  обоснования; package остаётся в статусе `draft`.

## Сверка с текущим draft.12

В [текущем source package](../candidates/domain-v0.2.0-draft.12/composition/domain-ontology-package.yaml)
`CIStatus` обозначает состояние **одной** status-check entry, а не агрегат;
счётчик проверок — отдельный результат измерения. Это рабочая граница draft,
не утверждение об истине или установленной GitHub availability. Выбранный в
[0011](../../docs/drafts/GITVIEW-SPEC-0011.yaml) принцип подсчёта отдельных
актуальных проверок ей соответствует. Сопоставление source entries, актуальной
revision, повторов и специальных исходов остаётся вопросом спецификаций и
проверки источника. Ни зелёная проверка, ни её цвет не доказывают mergeability.
