# Code и VersionControlSystem: граница действия

Статус: **предметный разбор и кандидат**, не утверждённое действие и не
новая версия ontology package. Он первоначально проводился для draft.10;
текущий рабочий контекст — `local.gitview.domain@0.2.0-draft-composition.13`,
где `versionControlsCode` по-прежнему объявлен через domain/range с открытыми
действием и возникающим свойством. Проверка терминов не устанавливает истинности
модели или выполнения действий.

## Основание и граница продукта

Владелец определил Repository как «Код, в котором действует Система Контроля
Версий», а Code — как по сути папку с файлами (`conversation:gitview/excerpt-24`
и `excerpt-25`). Ранее он связал Repository с доступом к истории изменений
исходного кода и назвал Git примером (`excerpt-18`). Это основание для понятий,
но не описание конкретного выполненного действия или полной файловой модели.

В draft.10 `versionControlsCode` связывает `VersionControlSystem` и `Code`;
его действие и возникающее свойство ещё не определены. Само наличие записи в
разделе `relations` не заполняет этот пробел. Здесь **отношение** в смысле
владельца — свойство, возникающее при действии актора над объектом; более общая
связь участников сама по себе не доказывает ни действие, ни актора.

GitView показывает наблюдаемые у источника объекты, состояния, счётчики и ссылки.
Ему не требуется загружать исходные файлы или исполнять VCS ради обзора. Это
граница потребностей приложения, а не отрицание существования кода, истории или
необходимости согласованной онтологии.

## Различимые интерпретации

| Кандидат | Что могло измениться | Что ещё нужно определить |
| --- | --- | --- |
| `RecordRevision` — запись версии | В истории конкретного Code появилась версия. | Является ли объектом действия сам Code или его история; как определяются их identity, версия и evidence записи. |
| `TrackCode` — постановка кода под контроль версий | Код оказался под управлением указанной VCS. | Что является предшествующим и последующим состоянием, когда управление начинается и прекращается; каким действием оно установлено. |

Имена — предложения для обсуждения, не объявления package и не доказательства
того, что это единственные действия. Запись версии не равна началу управления:
она может происходить в уже управляемой истории. Обратно, постановка под
контроль не обязана сама по себе означать появление новой версии. Одна запись
также не доказывает, что управление продолжается сейчас.

`VersionControlSystem` как субъект предложенного действия соответствует исходной
формулировке. Другой вариант — рассматривать человека или агента как актора,
а VCS как средство; для конкретного случая нужны основания. Не следует
автоматически объединять эти роли или выводить намерение из наличия системы.

Рекомендуемая следующая предметная проверка — `RecordRevision` как **узкий
кандидат**: он объясняет появление известной версии в истории, не требуя
изменения файлов в момент записи. Но он пока не объясняет всю семантику
`versionControlsCode`: источник identity Code и объекта действия остаётся
неопределённым. Поэтому package и определение отношения не меняются.

## Применение к спецификации GitView

В 0002 явно зафиксирована граница: подтверждённая identity Repository и
счётчик PR commits позволяют работать с этими наблюдениями, но не устанавливают
identity локальной Code-папки или конкретное действие VCS. Это не отменяет
исходную формулировку владельца о Repository и не требует загружать файлы.

Из двух предложений `RecordRevision` относится к возможной записи одной версии,
а `TrackCode` — к установлению управления; ни одно не обосновывает полностью
другое. До выбора нужна наблюдаемая граница до/после, identity объекта и
свидетельство действия. Поэтому новый actor/action в package не добавлен.

## Примеры для проверки модели

Это гипотетические примеры, не результаты работы приложения или источника.

1. Для одного подтверждённого Code было известно множество версий `{r1}`;
   достоверное наблюдение показывает запись `r2` данной VCS. Можно обсуждать
   действие записи и изменение известной истории на `{r1, r2}`. Из этого
   одного не следует, что содержимое файлов изменилось во время записи или что
   управление VCS действует бессрочно.
2. Счётчик PR commits изменился с 1 на 2. Без дополнительных данных нельзя
   установить конкретную новую версию, объект Code, действующего актора,
   полноту истории Repository или конкретное действие записи.
3. GitView получил число commits у PR. Он может показать этот счётчик с его
   областью и доступностью; ему не нужно доказывать конкретное действие VCS.
4. Источник подтвердил тот же GitHub Repository после rename или transfer.
   Правило identity сохраняет Repository и его membership; оно само по себе
   не определяет файловую identity Code и не доказывает действие над файлами.
5. Для `TrackCode` требуются различимые до/после и основание, связывающее
   изменение с действием. Одной записи версии или текущего source address
   недостаточно, чтобы установить момент начала управления.

## Решение для текущего объёма GitView — 15 ноября

Для завершаемой продуктовой спецификации сохраняем `versionControlsCode` как
**структурную связь-кандидат** между `VersionControlSystem` и `Code`, не как
формализованное действие или доказанное происшествие. Так трактуется её запись
`domain`/`range` в выбранном draft.13. Она поддерживает употребление понятий
в исходном описании Repository, но не отвечает на вопрос, каким действием и
когда возникло конкретное отношение. Это ограничение сохраняется в ontology.

`TrackCode` и `RecordRevision` не добавляются в рабочий package сейчас:
первый требует определить объект постановки под контроль и границу возникновения
управления, второй объясняет запись версии, а не возникновение или продолжение
управления. Для обзора PR, Issue, CI и счётчиков ни одно из этих действий не
является входом решения или пользовательским результатом. Выбор первого лишь
ради заполнения формального ребра добавил бы не обоснованную замыслом семантику.
Это не объявляет VCS пассивной и не отрицает возможность такой модели позже.

| Наблюдение или задача | Что допустимо утверждать | Чего оно не устанавливает |
| --- | --- | --- |
| Известен текущий контекст управляемого GitHub Repository | GitView может связать источник с подтверждённой identity Repository и показывать допустимые данные. | Identity конкретной локальной папки, начальное действие VCS и его время. |
| Изменилось значение PR commit count | Наблюдается другое значение счётчика в своём source context. | Какая именно версия записана, кто действовал и как изменилась папка. |
| Потребуется отдельно описывать реальные операции VCS | Модель можно расширить после выбора identity Code, роли актора и проверяемого перехода. | Ни текущее имя связи, ни успешная структурная проверка не выбирают это действие заранее. |

Это автономное рабочее решение о границе моделирования, не semantic approval
пакета, не фиксация действия в реальном мире и не запрет будущего расширения.
Оно снимает необходимость придумывать origin action для текущего обзора,
оставляя origin и продолжающееся управление открытыми для иной области задач.
Проверен смысл исходных определений и текущего package вручную; новый package,
SDK или выполненные VCS-операции не заявляются.

## Сверка потребителей на рабочем снимке

На GitView `fc1300e` поиск по 127 `GITVIEW-SPEC-*.yaml` по точным строкам
`gitview:Code`, `gitview:VersionControlSystem`, `gitview:versionControlsCode`,
`versionControlsCode`, `TrackCode` и `RecordRevision` нашёл только явное
упоминание связи в [0002](../../docs/drafts/GITVIEW-SPEC-0002.yaml). Сам 0002
отделяет identity Repository и PR commit count от identity Code, актора,
исполненного действия и непрерывного управления. В [0008](../../docs/drafts/GITVIEW-SPEC-0008.yaml)
и [0041](../../docs/drafts/GITVIEW-SPEC-0041.yaml) счётчик коммитов задан как
наблюдаемое свойство PR со своим контекстом; его нельзя считать свидетельством
конкретной операции над локальным Code.

Это ограниченный текстовый поиск и чтение трёх узлов, а не семантический
анализ всего графа: он не обнаруживает перефразированные предположения и не
доказывает отсутствие скрытых зависимостей. Новое действие в package не
добавлялось; необходимость моделировать его при расширении продукта остаётся
открытой.
