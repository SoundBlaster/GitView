# Issue hierarchy: текущие связи и наблюдения

Область — GitHub Issues, выбранные для GitView. Владелец выбрал родительскую
Issue, дочерние Issues и счётчики непосредственных sub-issues. Вопрос
доступности данных и способов их получения остаётся отдельным.

| Утверждение | Основание и граница |
| --- | --- |
| У Issue не более одного текущего непосредственного parent в указанном source context | [GraphQL Issue](https://docs.github.com/en/graphql/reference/issues) имеет единичное поле `parent`; `replaceParent` и [REST sub-issues](https://docs.github.com/en/rest/issues/sub-issues) описывают замену текущего parent. Это документальное основание, не live-проверка адаптера GitView. |
| У parent может быть несколько непосредственных детей | GraphQL `subIssues` — connection; неполная connection не доказывает полный состав. |
| Child → parent и parent → child имеют обратный смысл | Это семантическое соответствие одной непосредственной source-связи при совместимых identity, scope, времени и access; не доказательство, что оба независимых запроса успешно получили данные. |
| Прямой ребёнок и произвольный потомок различаются | Если A → B → C, C не является непосредственным ребёнком A только из этой цепочки. Счётчик детей не является числом выполненных задач. |
| Исторические parents могут отличаться | Перепривязка не делает A и B одновременными текущими parents. При неупорядоченных конфликтующих наблюдениях актуальный parent остаётся uncertain. |
| Нет наблюдения parent | Ошибка, скрытое или пропущенное поле не доказывают отсутствие; достоверное отсутствие требует достаточного source evidence и access. |

В draft.10 `issueParent` описывает **текущее** отношение child → parent с
кардинальностью `0..1`; `issueSubIssue` — parent → direct child с
`0..*`. Кардинальность — ограничение модели текущего состояния, а не
требование отбрасывать конфликтующие исходные свидетельства, дополнять
частичные списки или доказывать непрерывную историю. Это не акторное
отношение в смысле, который объяснил владелец: source-связь и действие,
породившее её, различны. Идентичность актора и факт выполненной операции
по одной связи не восстанавливаются.

Ни совпадение номеров в разных Repository, ни одно видимое ребро не
устанавливает полную иерархию, текущий счётчик, доступность скрытых объектов
или завершённость работы. Product contract и сценарии — в
[0078](../../docs/drafts/GITVIEW-SPEC-0078.yaml). Source documentation
поддерживает предметную модель, но конкретная API selection, permissions,
полнота страниц, реальный source behavior и enforcement кардинальности
остаются непроверенными; compiler check сам по себе этого не доказывает.
