# GitView domain ontology — draft 0.1.0

Это черновой словарь проекта для обсуждения и согласованности будущих
спецификаций. Он не является принятым ontology package, спецификацией приложения
или описанием реализованного поведения. Source package:
[`domain-ontology-package.yaml`](domain-ontology-package.yaml).

Источники — пользовательские цитаты в Git-tracked SpecDraft sketch:
`conversation_memory/sketches/gitview`, ревизия
`fae218b80fa3496c94df47560997b2c6`. Ссылки `excerpt-*` — локальные ссылки на
фрагменты беседы, а не удостоверенные ID сообщений. Точный текст и авторы
сохранены в соответствующих узлах sketch. Схема и выбор базовых классов ниже —
предложение агента; наличие цитаты не означает утверждение конкретного YAML.

## Термины и происхождение

| Термин | Смысл в текущем обсуждении | Источник |
| --- | --- | --- |
| `Project` | Проект GitView; состав репозиториев рассматривается отдельно. | `excerpt-10`, `excerpt-11`, `excerpt-12` |
| `Code` | Код как папка с файлами; границы понятия ещё не определены. | `excerpt-25` |
| `VersionControlSystem` | Система, действующая над кодом; названный пример — Git. | `excerpt-18`, `excerpt-24` |
| `Repository` | Код, в котором действует система контроля версий. | `excerpt-24` |
| `GitHub` | В обсуждённом отношении выступает актором, управляющим репозиторием и потоком изменений. | `excerpt-19`, `excerpt-20` |
| `Issue` | Объект GitHub; в рассматриваемой цепочке выступает мотивом для актора. | `excerpt-01`, `excerpt-22`, `excerpt-23` |
| `PullRequest` | PR, связанный с предлагаемыми изменениями; в рассматриваемой цепочке — последствие действия. | `excerpt-01`, `excerpt-14`, `excerpt-23` |
| `ReviewThread` | Тред, важный при оценке review; пользователю нужны в том числе долго длящиеся обсуждения. | `excerpt-02`, `excerpt-14` |
| `CIStatus` | Состояние CI для обзора, в том числе сигнал ошибки. Это предложенное агентом имя; источник и смысл ещё нужно уточнить. | `excerpt-02`, `excerpt-14` |
| `Metric` | Измерение для обзора; названы строки, коммиты, прогоны и треды. | `excerpt-03`, `excerpt-14` |

`sg:DomainEntity` и `sg:ValueObject` — технические базовые классы из выбранного
foundation. Их применение здесь является черновым моделированием, а не
решением о постоянной роли актора, идентичности или структуре данных.

## Отношения, связи и действия

Схема Ontology требует хотя бы одно объявление relation. Здесь приведены две
кандидатные декларации, основанные на словах пользователя: система контроля
версий действует над `Code` (`versionControlsCode`), а GitHub управляет
`Repository` (`managesRepository`). Это типы направленных связей в формате
compiler, а не зафиксированные экземпляры действий. Схема сама по себе не
подтверждает актора, действие, возникшее свойство или жизненный цикл отношения.

Пользователь различает менее конкретную **связь** и **отношение** как свойство,
возникающее при действии актора над объектом (`excerpt-21`). Отношение может
сохраняться после действия. Какие роли, события и свойства нужны для точного
представления каждой декларации — открытый вопрос.

Для `Project` и `Repository` сохранены следующие договорённости
(`excerpt-10`): проект содержит один или несколько репозиториев; репозиторий
может входить в разные проекты; по умолчанию один проект — один репозиторий.
Это правило состава, а не введённый здесь экземпляр отношения. Актор и действие,
создающие членство, пока не определены. Отдельный термин `Group` сейчас
избыточен (`excerpt-11`, `excerpt-12`). GitHub organizations — метаданные;
проект может включать репозитории разных organizations.

`GitHubRepository` — контекстное обозначение Repository, находящегося в
отношении управления со стороны GitHub (`excerpt-19`, `excerpt-20`, уточнение
`excerpt-31`). Пользователь описывает происхождение отношения как
`GitHub → Action on → Repository`: GitHub действует над Repository, а
Repository в этом отношении именуется GitHubRepository. Вложенность в HC
показывает эту предложенную композицию, но сама не кодирует действие.

Пользователь предложил аналогию с **Decorator**: «GitHub как бы декорирует
Repository» (`excerpt-32`). Она поясняет сочетание исходного Repository с
GitHub-специфическими свойствами и возможностями. Это концептуальная аналогия;
выбор программного паттерна, интерфейсов и способа реализации остаётся отдельным
архитектурным вопросом. Происхождение отношения управления через действие
GitHub сохраняет смысл, описанный выше.

GitView сейчас ожидает GitHub-специфические свойства репозитория; их точный
набор ещё предстоит определить. GitLab и BitBucket могут рассматриваться позже.
Обобщения `GitManagementSystem` и `ManagedRepository` для текущего продукта
пока избыточны. Техническое представление контекстного имени, идентичность и
жизненный цикл отношения остаются открытыми; это уточнение не добавляет
отдельный compiler-класс автоматически.

### Обсуждённый пример действия

```text
Issue — мотив → актор — меняет → Code → последствие: PullRequest
```

Это зафиксированная концептуальная цепочка (`excerpt-21`–`excerpt-23`), а не
утверждение, что любой PR имеет Issue или что актор и мотив выводятся из ссылки
на Issue. Одна из возможных ролей актора — человек, coding agent или процесс;
конкретное связывание ролей и источники данных ещё не согласованы. PR не
означает merge. Как представить `PR` и изменение кода в состоянии и Delta —
вопрос для следующей итерации, а не принятия этой цепочки компилятором.

В Ontology уже есть черновые пакеты `events-core` и `motivation-core` с
контекстными ролями и `Motive` / `MotivationHypothesis`. Они не дублируются
локальными классами. Исходный контекст этого пакета использует foundation;
последующий [пилот композиции](../../pilots/motivation-composition/README.md)
отдельно проверяет импорт двух draft packages и ссылку на `motivcore:Motive`.
Он не заменяет текущий контекст и не утверждает семантику модели.

## Границы и вопросы

- Название, ID, бейджи и текст относятся к компактному обзору; какие поля
  применимы к каждой сущности, ещё не определено (`excerpt-15`). Кнопки и
  жесты не становятся ontology concepts лишь потому, что есть в UI (`excerpt-17`).
- Какие именно строки, прогоны и треды входят в метрики, как трактуются их
  единицы, диапазон, источники и актуальность? (`excerpt-14`)
- Как различать ожидающий review, готовый, проблемный и неизвестный результат?
  Красный CI, длинный тред и объём работы не являются взаимозаменяемыми сигналами.
- Как соотносятся Git worktree, история и рассматриваемая папка с файлами, в
  том числе для удалённого репозитория? Достаточно ли исходной модели Code?
- Как выразить `GitHub Repository` и membership с контекстными ролями и
  действием, не придумывая отдельную сущность или наследование?
- Необходимость общей метасущности с динамическими свойствами остаётся
  гипотезой (`excerpt-14`); она не введена в пакет.

Формальная проверка структуры не заменяет ответы на эти вопросы, проверку
естественного языка или утверждение пакета владельцем проекта.

## Проверка и использование

[`ontology/context.yaml`](../../context.yaml) выбирает этот пакет и закрепляет
SHA-256 исходника и нормализованного IR. Он указан в `specgraph.project.yaml`
как текущий **черновой** контекст. Выбор контекста не означает утверждения
терминов и не включает автоматический gate.

Проверка 1 ноября 2026 года: `ontologyc check` и `ontologyc compile` прошли;
native runtime SpecGraph `39b66a60` при вызове `ontology-context` в самом
GitView вернул `verified`, `semantic_approval: not_established` и
`canonical_mutations_allowed: false`. Профиль `ontologyc-foundation-v1`
проверил структуру и разрешение foundation-ссылок, но не проверял смысл
естественного языка. Использован локальный `ontologyc` с SHA-256
`98c5e50f3b779888fc290ec4159e29d6dd0179ac9f4706ec476bec327bb5f847`;
происхождение бинарника отдельно не удостоверялось.

На временной копии **этого же** пакета отдельный синтетический spec показал
`Project`, `Repository`, `Issue`, `PullRequest` и `Metric` как кандидатов
совпадения, а намеренно добавленный `Group` — как неизвестный термин. После
изменения исходника без обновления hash context вернул `invalid`. Исходный
пакет GitView и его `specs/nodes/` при этих контролях не менялись. Отчёты и
генерируемый SDK находятся в рабочем каталоге проверки на TB5:
`/Volumes/TB5/Developer/Builds/GitHub/GitView-a40d73ccf162f8d8/ontology/gitview-ontology-bfyv4hcz/`.

Для повторной проверки нужен установленный SpecGraph runtime и отдельно
доступный `ontologyc`:

```sh
specgraph-runtime --workspace /path/to/GitView ontology-context -- \
  --ontologyc /path/to/ontologyc --compiler-sha256 <sha256-исполняемого-файла>
```

При изменении source package нужно заново скомпилировать его на проверенном
TB5, обновить выбранный `generated/ontology.normalized.json` и оба hash в
`ontology/context.yaml`, затем повторить проверку. Остальные файлы SDK и отчёты
проверки являются build artifacts и не являются частью принятой онтологии.
